# StockMind 프로젝트 역할 분담

국내(KOSPI·KOSDAQ)·미국(NASDAQ) 주식의 시세·지수·환율·재무·공시를 수집해 PostgreSQL에 구조화하고, FastAPI 조회·분석 API와 바닐라 HTML/CSS/JS 화면으로 제공하는 주식 분석 대시보드를 4인 팀(시니어 1 · 주니어 3)이 개발했다.

AI 코딩 도구(Claude Code)를 활용하는 팀에서 생기기 쉬운 문제 — 기능 중복 개발, AI가 생성한 코드를 아무도 설명하지 못함, 프론트·백엔드 규격 불일치, 마지막 날 처음 통합 — 를 막기 위해 다음 세 가지 원칙으로 운영했다.

1. **기술 영역별 담당** + **기능별 오너(Feature Owner)** 를 함께 둔다.
2. 단계(Stage)마다 **인터페이스(API 응답·DB 스키마·함수 입출력)를 먼저 합의**하고 병렬 개발한다.
3. AI가 작성한 코드는 담당자가 **파일 단위로 설계 설명을 듣고 승인한 뒤** 생성하며, 담당자가 직접 설명할 수 있어야 PR을 올린다.

## 1. 팀 구성

> 1차 세미프로젝트 규격상 LLM 연동은 범위 밖이므로, 일반적인 "AI 담당" 자리를 **데이터 수집·분석 로직** 담당으로 바꿨다. 매력도 다중 팩터 모델이 이 프로젝트의 분석 엔진 역할을 한다.

### 팀원 A — 프론트엔드 및 사용자 경험 (주니어)

화면 개발 · API 연동 · UI 상태 처리

- 화면 구조와 사용자 흐름 설계 (홈 · 주식 리스트 · 종목 상세 · 모의 포트폴리오)
- 공통 컴포넌트(검색, 투자 성향 메뉴, 관심 토글, 담기 모달, 차트) 개발
- API 연결, 로딩·빈 상태·오류 상태 처리, 반응형(모바일)
- 사용자 관점 기능 테스트, 화면 스크린샷

주요 산출물: `frontend/*.html`, `frontend/js/pages/*`, `frontend/js/components/*`

### 팀원 B — 백엔드 API 및 DB (주니어)

API · SQL · 입력 검증 · 사용자 데이터 CRUD

- 조회용 VIEW·SQL 작성 (CTE · 윈도우 함수 · 집계)
- FastAPI 라우터·Pydantic 스키마·입력 검증·에러 코드
- 관심종목 CRUD, 소유자 확인(남의 리소스 404), 통계 API
- 국내·미국 재무·공시 수집(DART · SEC EDGAR)과 조회 API

주요 산출물: `backend/app/api/*`, `backend/app/queries/*.sql`, `backend/db/views.sql`, API 테스트

### 팀원 C — 데이터 수집 및 분석 로직 (주니어)

수집 파이프라인 · 전처리 · 계산 로직 · 점수 모델

- 유니버스 설정, 샘플·실데이터 적재, 전처리(중복·이상 행 격리)
- 시세·지수·밸류에이션 Provider(pykrx · yfinance)
- 모의 포트폴리오 계산(Decimal, 환율 효과 분리), 환율 TTL 서비스
- 매력도 다중 팩터 모델(로버스트 Z · 섹터 중립화 · 프리셋 가중), 시장 심리 지수·섹터 히트맵

주요 산출물: `backend/app/ingest/*`, `backend/app/providers/*`, `backend/app/services/*`, 계산 테스트

### 팀원 D — 기술 통합 및 배포 책임 (시니어, 팀장)

아키텍처 · 통합 · 운영 안정성 · 일정

- 전체 구조와 인터페이스 계약 확정, 단계별 범위 정의
- Git 브랜치·PR·코드 리뷰 규칙, Claude Code 작업 규칙(`CLAUDE.md`) 관리
- Docker Compose 환경, 갱신 스케줄러·TTL·동시 실행 방지(advisory lock), 헬스체크
- 단계별 통합·충돌 해결·통합 테스트, 최종 문서

주요 산출물: 단계별 통합 서비스(태그 v1~v5), 배포 환경, 아키텍처·운영 문서

D는 회의 관리자가 아니라 **각 단계에서 가장 결합도가 높은 조각을 직접 구현**하면서 통합을 책임진다.

## 2. 기능별 오너

모든 기능에 완료를 확인하는 오너 1명을 둔다. 오너가 코드를 전부 쓰는 것은 아니지만, 화면 → API → DB → 다시 화면까지 동작하는지 확인하는 책임은 오너에게 있다.

| 단계 | 기능 | 주 담당 | 협업 | 완료 기준 |
|---|---|---|---|---|
| 0 | 프로젝트 뼈대·개발 환경 | D | — | `docker compose up` 후 `/health/db` 200, 빈 화면 셸 표시 |
| 1 | 샘플 데이터 적재 | C | D | `init-db` → `sample` 적재 후 종목·일봉·지수·환율 행 존재 |
| 1 | 주식 리스트·종목 상세 조회 | B | A | 리스트 정렬·필터, 상세 기본 정보·일봉 차트가 화면에 표시 |
| 1 | 지수·환율 카드 | A | B | 홈에서 지수 5개 + USD/KRW 등락·스파크라인 표시 |
| 2 | 관심종목 CRUD | B | A | 추가·정렬·메모·목표가·삭제가 화면에서 동작, 중복 409 |
| 2 | 모의 포트폴리오 | C | A, B | 수량/금액/비중 담기, 시드 초과 409, 평가손익·환율 효과 분리 |
| 2 | 사용자 확정·소유자 검사 | D | B | 남의 포트폴리오 접근 시 404 |
| 3 | 국내·미국 시세 실데이터 | C | D | pykrx·yfinance로 2년 일봉·지수·밸류에이션 적재, 실패는 대상별 로그 |
| 3 | 재무·공시 | B | A | DART·SEC 재무 5개년·공시 1년 적재, 상세 화면 탭 표시 |
| 3 | 4시간 TTL 갱신·스케줄러 | D | C | TTL 이내 SKIPPED, 부분 실패 30분 뒤 재시도, 사이드바 갱신 시각 |
| 4 | 매력도 점수 모델 | C | D | 프리셋 4종 점수·팩터 기여도 저장, 단위 테스트 통과 |
| 4 | 수치 분석·경쟁 비교·통계 API | B | C | analysis·peers·statistics 응답이 정의서 예시와 일치 |
| 4 | 종목 상세 분석 화면 | A | B | 게이지·기여도·레이더·경쟁 추이·월별 요약 표시 |
| 4 | 비교군(benchmark)·섹터 중립화 | D | C | 비교군 선정·평시 데이터 적재, 같은 국가끼리 중립화 |
| 5 | 메모·목표가·통계 확장 | B | A | 메모·목표가 수정, 월별·랭킹·데이터 품질 API |
| 5 | 균등 배분 미리보기 | C | A | 관심종목 균등 배분 계산(저장 안 함), 제외 사유 표시 |
| 6 | 시장 심리 지수·섹터 히트맵 | C | A | 일 1회 계산해 DB 저장, 홈에서 재사용(외부 호출 없음) |
| 6 | 홈 위젯 API·상단 검색 | B | A | 거래량 급증·매력도 순위, 상장 목록 검색 자동완성 |
| 6 | 홈 대시보드 개편 | A | B, C | 2열 배치·관심종목 컴팩트·히트맵·심리 지수 |
| 6 | 최종 통합·문서·배포 | D | 전원 | 새 환경에서 README 5분 시작하기로 재현 |

## 3. 개발 순서 — 단계별 반복

각 단계는 같은 사이클을 돈다.

1. **범위·완료 기준 합의** — D가 단계 문서와 파트별 시작 프롬프트를 배포
2. **인터페이스 먼저** — API 응답 JSON·DB 테이블·함수 시그니처를 정의서(`docs/06`·`docs/05`)에 먼저 적는다. 프론트는 이 예시 JSON을 목(mock)으로 먼저 화면을 만든다
3. **각자 Claude Code로 구현** — 담당 파일만 수정, 파일 하나씩 설계 설명 → 승인 → 작성 → 해설
4. **PR → 리뷰 → 단계 브랜치에 머지** — 테스트 통과·담당자 설명 가능·계약 일치를 확인
5. **D가 통합·시나리오 검증** — 화면 입력 → API → DB → 화면 표시 전체 흐름 확인 후 `main` 머지·태그

| 단계 | 결과물 | 태그 |
|---|---|---|
| Stage 0 | 뼈대·개발 환경 | v0.1 |
| Stage 1 | MVP — 샘플 데이터로 리스트·상세·지수 | v1.0 |
| Stage 2 | 사용자 기능 — 관심종목·모의 포트폴리오 CRUD | v2.0 |
| Stage 3 | 실데이터 — 4개 소스 수집·4시간 갱신 | v3.0 |
| Stage 4 | 분석 — 매력도·경쟁 비교·통계 | v4.0 |
| Stage 5 | 고도화 — 메모·목표가·통계 확장·운영 안정성 | v5.0 |
| Stage 6 | 홈 대시보드 개편·상단 검색·최종 문서 | v6.0 |

## 4. 팀 운영 규칙

| 규칙 | 운영 방법 |
|---|---|
| 작업은 한 명이 책임진다 | 모든 파일·기능에 담당자 1명. 담당 외 파일은 수정하지 않고 요청한다 |
| 작업 크기를 작게 | 브랜치 하나 = 기능 하나, 커밋 하나 = 파일 하나(또는 파일+테스트) |
| 인터페이스 먼저 | 단계 시작 시 응답 JSON·스키마를 정의서에 먼저 기록 |
| PR로만 통합 | `feat/s{단계}-{a,b,c}-{기능}` → `stage{N}` → `main`. 리뷰 1명 승인 필수 |
| 기다리지 않고 병렬 | 앞 순서 작업이 머지 전이면 Draft PR로 먼저 리뷰받고, 머지 후 최신 stage를 합쳐 같은 PR을 Ready로 전환. D는 Ready PR만 머지 순서대로 머지 |
| AI 코드는 이해하고 넘겨야 | 파일·파트마다 보기 3개 확인 질문, 고른 답을 PR "핵심 개념" 칸에 기록. 리뷰에서 물어볼 수 있음 |
| 매일 15분 공유 | 어제 완료 · 오늘 완료 예정 · 막힌 부분만. 기술 토론은 해당자끼리 따로 |

## 5. Claude Code 사용 규칙 (요약)

레포 루트의 `CLAUDE.md`에 강제 규칙으로 들어 있다.

- 첫 응답은 **작업 계획표**(만들 파일·순서·각 파일 역할·의존 계약)만 내고 승인을 기다린다.
- 파일마다 **[설계 설명] → 승인 → [작성] → [코드 해설] → [이해 확인 질문] → [테스트]** 순서.
- 여러 파일 동시 생성 금지, 담당 외 파일 수정 금지, 이번 단계 범위 밖 기능 추가 금지.
- "만들어줘"처럼 막연한 요청이 와도 위 절차로 되돌린다.
- (Stage 1부터) 주니어에게 하는 설명·계획은 **입문자 기준의 쉬운 말**로 쓴다. 코드·설계 수준은 그대로이고, 리뷰어용 정밀 내용은 "기술 메모" 칸에 따로 남긴다.
- (Stage 1부터) 작업 시작·PR 준비·선행 머지 때 Claude가 **묻지 않고 최신 코드를 받는다**(fetch → stage 브랜치 merge).
- (Stage 1부터) 다른 팀원 파일이 아직 없어도 계약(프롬프트·docs/05·06·원본)대로 **묻지 않고 진행**한다. 임시 MOCK·미룬 테스트는 표시해 두고 Ready 전환 때 정리한다.
