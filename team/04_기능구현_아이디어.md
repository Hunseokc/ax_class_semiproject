# 추가 기능 구현 (아이디어 레벨)

## 전제

이 문서는 stage7 계획의 재료가 될 아이디어를 모은 메모예요. 계획과 구현은 stage6 완료와 diff 0 확인 뒤에 시작해요. diff 0은 약속 영역(DB·API·파일 경로·이름·시그니처·기능 목록)이 원본 semi와 같다는 뜻이에요. 화면 표현(배치·색·문구·CSS)은 PR "원본과 다르게 한 것"에 기록된 차이만 예외로 둬요.

- 지금은 코드를 만들지 않아요. 이 문서는 team/ 메모라 diff 0 비교 대상(약속 영역)에 들어가지 않아요.
- 아이디어는 두 가지예요.
    - ① 시장 컨디션 점수
    - ② 노출 종목을 늘리기 위한 데이터 수집 확장

## 아이디어 1. 시장 컨디션 점수

종목 매력도 옆에 "시장 분위기"를 따로 보여주자는 아이디어예요. 계산은 비교군 일봉으로 하는 추세 breadth 방식을 쓰고, 추가 API 호출은 없어요.

### 레퍼런스: knowingasset MARKET CONDITION

[knowingasset 주식 화면](https://knowingasset.com/web/stocks)의 박스를 확인했어요. S&P 500 구성종목 506개의 종가로 지표 5개를 만들고, 각각 0~100으로 바꾼 뒤 평균을 내요.

| 지표 | 뜻 | 예시(10/15 마감) |
| --- | --- | --- |
| 200일선 위 | 200일 이동평균 위에서 마감한 종목 비율 | 51% |
| 50일선 위 | 50일 이동평균 위에서 마감한 종목 비율 | 44% |
| 오른 종목 | 전날보다 오른 종목 비율 | 75% |
| 52주 신고가 근접 | 1년 최고 종가의 95% 이상인 종목 비율 | 16% |
| 신고가·신저가 | 1년 신고가·신저가 종목 수 | 23 · 0 |
- 점수 구간: 60 초과 좋음, 45 이하 나쁨, 그 사이 보통
- 표기: "53 / 100 보통", "▲11 · 보통 1일째", 한 줄 요약("고르게 올랐어요"), 3개월 추이 차트
- 안내 문구: "시장 분위기를 보는 참고 지표이며 투자 판단의 근거가 아니에요"

### 추세 방식을 고른 이유

- **틀릴 수 없는 사실이에요.** "200일선 위 51%"는 이미 일어난 일을 센 것이라, "그냥 수치 판단입니다"라는 안내와 잘 맞아요.
- **예측형은 빼요.** 선물이나 VIX로 "오늘 떨어질 것" 같은 말을 하면 빗나갈 수 있어요.
- **구현이 단순해요.** 종가와 이동평균만 있으면 돼요.
- **한계:** 늦게 반응해요. 하루 만에 급락하는 날은 다음 날 점수에 반영돼요.

### 우리 계산안: 비교군 기반 breadth

레퍼런스와 같은 지표 5개를 비교군 일봉으로 계산해요. 한국과 미국을 각각 내요.

- 비교군은 국가별 9개 섹터 × 섹터당 최대 50종목이고, 일봉 400일치를 갖고 있어요. 200일선 계산에 충분해요.
- 노출 25종목만으로는 표본이 작아서, 몇 종목만 움직여도 점수가 크게 출렁여요.
- 참고: 금융·보험·부동산은 비교군에서 빠져 있어요. 섹터를 고르게 뽑은 대형주 표본이라 지수 구성과는 조금 달라요.

### 표기 원칙

- 기준 시점을 꼭 붙여요. 예: "10/15 마감 기준"
- 처방하지 말고 묘사해요. "시장 흐름이 약해요"는 되고, "오늘은 사지 마세요"는 쓰지 않아요.
- 종목 점수와 시장 점수는 합치지 않고 따로 보여줘요.
- 안내 문구는 레퍼런스처럼 "참고 지표이며 투자 판단의 근거가 아님"을 박스 안에 둡요.

## 데이터 구조 현황

종목은 세 층으로 나뉘어 있어요. 화면에서 항상 25개로 보이는 건 노출 종목 수이고, 점수 계산 표본은 따로 있어요.

| 구분 | 규모 | 받는 데이터 |
| --- | --- | --- |
| 노출 종목 | 25개, 고정 | 일봉, 밸류에이션, 재무 5년, 공시 |
| 비교군(benchmark) | 국가별 9개 섹터 × 최대 50종목, 최대 약 900개 | 일봉 400일, 재무 3년 |
| 상장 목록(listed) | 코스피·코스닥·NASDAQ·NYSE 보통주 전체 | 이름·티커만, 상세를 열 때 받음 |
- 비교군 설정: `semi/backend/config/universe.yaml`의 `benchmark`(per_sector 50, us_rank_pool 1500, price_days 400, reselect_days 30)
- 미국은 시가총액 상위 1,500개 안에서 섹터별로 골라요.

**노출 수를 25개로 둔 이유:** 노출 종목은 재무와 공시까지 받아요. 25개만 처음 전체 적재해도 257초가 걸렸고, DART·SEC·yfinance에는 각각 호출 한도가 있어요. 그래서 "보여줄 종목"과 "비교에 쓸 종목"을 나눠 두었어요.

## 아이디어 2. 데이터 수집 확장

노출 종목을 늘리려면 호출량을 늘리기보다 호출 방식을 바꿔요. 시장 전체를 한 번에 받고, 바뀐 것만 다시 받는 것이 핵심이에요.

| 대상 | 지금 방식 | 바꿀 방식 |
| --- | --- | --- |
| 시세(한국) | 종목별 호출 | pykrx에 날짜를 주고 전 종목을 한 번에 받기. 원본 `load_prices_bulk`가 같은 발상 |
| 재무(미국) | 회사별 companyfacts 호출 | SEC가 매일 밤 올리는 전 종목 재무 zip 파일 하나 내려받기 |
| 재무(한국) | 회사·연도마다 `fnlttSinglAcntAll`, 회사마다 `list.json` | 날짜만으로 `list.json`을 불러 어제 정기공시한 회사만 재무 다시 받기 |

### DART 호출량 계산

회사당 약 5번(재무 3년 × 1~2번 + 공시 목록 1번)이에요. 일일 한도는 키 1개에 약 2만 번이에요.

| 대상 | 처음 전체 적재 | 평소 갱신(공시 기반) |
| --- | --- | --- |
| 비교군 한국 약 450개 | 약 2,250번 | 하루 수십 번 |
| 국내 상장사 전체 약 2,500개 | 약 12,500번, 하루 안에 가능 | 실적 시즌에도 수천 번 |

### 쓰지 않을 방법: 인증키 로테이션

팀원 4명의 키를 돌려 쓰는 방식은 쓰지 않아요. 인증키는 개인에게 발급돼서 여러 키로 한도를 넘기면 이용 목적에 어긋나고, 확인되면 4개 키가 함께 정지될 수 있어요. 위 계산처럼 키 1개로도 충분해요.

### 참고: 상용 서비스의 데이터 수집

- yfinance는 비공식 라이브러리라 유료 버전이 없고, 약관상 개인 용도예요.
- 상용 서비스는 유료 업체를 써요. 미국은 Polygon.io, Tiingo, EODHD, FMP 등이고, 한국은 코스콤·KRX 데이터 상품과 증권사 API(KIS Developers, 키움 REST API)예요.
- 호출량보다 시세 재배포 라이선스 비용이 더 커요.
- 업체별 요금과 한도는 자주 바뀌어서 계획 단계에서 다시 확인해요.

## 아이디어 2-1. 우선순위 백그라운드 적재

사용자가 찾을 확률이 높은 기업부터 미리 받아 두는 아이디어예요. 상세를 열 때 기다리는 일이 줄고, 한도 안에서 커버리지가 매일 늘어요.

### 우선순위 기준

- **시가총액 순위:** 한국은 pykrx 전 종목 시가총액 한 번 호출, 미국은 원본 benchmark.py처럼 SEC 발행주식수 × 종가
- **거래대금 순위:** 거래량(주식 수)보다 거래대금(금액)이 낫아요. 거래량은 주가가 낮은 종목이 위로 올라와요.
- 두 순위는 매일 받는 bulk 시세에서 바로 나와서 추가 호출이 거의 없어요.

### 흐름

1. 매일 07:00 갱신 뒤 우선순위 큐를 다시 만들어요. 순서는 노출 종목 → 비교군 → listed 상위 순이에요.
2. 하루 예산을 정해요. 예를 들어 DART 한도의 일부만 백그라운드에 쓰고, 나머지는 평소 갱신과 상세 요청에 남겨 두어요.
3. 예산 안에서 아직 안 받은 기업을 위에서부터 받아요.
4. 사용자가 상세를 열면 그 기업은 큐를 건너뛰고 바로 받아요. 지금의 상세 열기 흐름(detail_ttl_hours 24)을 그대로 써요.
5. 한 번 받은 기업은 공시 기반 증분 갱신으로만 유지해요.

원본에는 이미 advisory lock(중복 호출 방지)과 `WindowLimiter`(호출 속도 제한)가 있어서, 백그라운드 작업과 상세 요청이 겹쳐도 중복 호출 없이 돌아가요. 다만 잠금을 묶음 전체에 걸어서 상세 요청이 오래 기다릴 수 있어요. 아래 "실적 시즌 부하 분산"에서 같이 풀어요.

### 실적 시즌 부하 분산

실적 시즌(3월 말~4월 초)과 30일 재선정이 겹치면 매일 07:00 비교군 갱신에서 재무를 받을 회사가 몰려요. DART 하루 한도(약 2만 번)는 충분하고 Job이라 시간 제한도 없어요. 문제는 잠금 범위예요.

`jobs.load_financials`는 대상 종목 전체가 끝날 때까지 DART 잠금을 한 번에 잡아요.

```python
with advisory_lock(engine, DART_LOCK_KEY):      # 몇백 개 종목 내내 유지
    return _load_financials(engine, providers, refs, years)
```

| 문제 | 상황 |
| --- | --- |
| ① 상세 요청이 멈춤 | 300개면 회사당 약 4번 × 300 ÷ 분당 90번(`WindowLimiter(90, 60.0)`) ≈ 13분 이상 잠금 유지. 그동안 비교군·상장 종목 상세를 열거나 관심종목에 추가하면 Hydrator(작업자 1개)가 잠금을 기다려 뒤 요청까지 모두 "loading" |
| ② 미국 종목도 기다림 | 같은 목록에 SEC 대상 미국 종목이 섞여, DART와 상관없는 미국 재무도 같은 잠금 안에서 처리 |
| ③ 연결이 끊기면 잠금이 풀림 | 세션 잠금이라 DB 연결을 수십 분 유지해야 해요. 풀러가 중간에 끊으면 잠금이 조용히 풀려 다른 작업이 DART를 동시에 부를 수 있어요 |
| ④ 점수 기준 연도가 섞임 | 실적 시즌 동안 일부는 새 연도, 일부는 지난해 재무로 섹터 비교. 지금도 있는 현상이고, 갱신이 몰려 늦어지면 기간이 길어져요 |

**해결안 (위 흐름과 같은 구조로 함께 구현)**

1. **회사 단위 잠금:** 회사 하나를 받을 때만 잠금을 잡아요. 상세 요청이 회사 사이에 끼어들어 바로 처리되고(①), 연결을 오래 붙잡지 않아요(③).
2. **하루 재무 예산:** 07:00 작업은 유효기간이 가장 오래 지난 순으로 정해진 수(예: 100개)까지만 받고 나머지는 다음 날로 넘겨요. 실적 시즌·재선정이 겹쳐도 하루 작업량이 일정해요. 사용자가 연 종목은 예산과 상관없이 바로 받아요.
3. **국가별 잠금:** DART(한국)와 SEC(미국) 잠금을 나눠요(②).
4. **기준 연도 표기:** ④는 막을 수 없어서 점수 옆에 "재무 기준 FY2025 n개 / FY2024 m개"처럼 보여줘요. 지금의 `data_quality` 구조에 넣을 수 있어요.
- stage7 전에 배포하면: 07:00 작업은 이용자가 적은 시간이라 ①의 영향이 작아요.

- 노출 종목을 몇 개까지 늘릴지, 화면 구성은 어떻게 바꿀지 정하기
- 아이디어를 몇 번째 파트로 나눌지, 팀원 복사·다듬기 범위와 D 구현 범위 나누기

# 실시간 시세 미지원 사유 및 향후 시세 구조

## 1. 발표 답변 (한 줄)

> "무료 API는 실시간 데이터가 아니라서 실시간 시세는 불가능합니다. 분석용 데이터는 일 단위면 충분하므로 pykrx로 일괄 수집하고, 최신성이 필요한 관심종목만 증권사 공식 API(KIS REST)로 보완하는 구조를 다음 단계로 계획하고 있습니다."
> 

## 2. 무료 API로 실시간이 불가능한 이유

**① 데이터 자체가 실시간이 아님**

| 소스 | 데이터 시점 |
| --- | --- |
| pykrx | 일별 데이터 (전일 종가 기준) |
| yfinance (.KS/.KQ) | 약 20분 지연 시세 |
- 아무리 자주 받아도 실시간은 되지 않습니다. 다만 yfinance 장중 시세는 전일 종가보다는 최신입니다.

**② 요청 한도 (20종목 × 5초 갱신 기준)**

- 요청 수: 초당 4회, 시간당 14,400회
- yfinance의 비공식 한도로 흔히 인용되는 IP당 2,000회/시간 기준으로 **약 8분 만에 소진**됩니다.
- 일일 한도 48,000회 기준으로는 **약 3시간 20분**이면 소진되어, 장 마감(6.5시간)까지 버티지 못합니다.
- `yf.download()`로 묶어서 요청하면 시간당 720회로 한도 안에 들어옵니다. 다만 요청 수가 줄 뿐이고 20분 지연은 그대로입니다.

**③ 클라우드 IP 차단**

- Yahoo는 클라우드(데이터센터) IP를 더 쉽게 차단해서, 로컬에서는 되는데 배포 후 429 오류가 나는 경우가 많습니다.
- 프로젝트는 이미 yfinance 1.7.0을 써서 라이브러리 쪽 회피책은 적용된 상태입니다.
- 고정 IP로 바꿔도 구글 클라우드 대역이라 해결되지 않습니다.
- 근본 해결은 공식 API로 바꾸는 것뿐입니다.

**④ Cloud Run 기본 설정과 맞지 않음**

- 요청이 있을 때만 CPU가 할당되어, 5초마다 미리 받아두는 백그라운드 루프가 제대로 돌지 않습니다.
- 최소 인스턴스가 0이라 콜드 스타트 시 첫 응답이 수 초~10초 걸립니다.
- 인스턴스가 늘어나면 메모리 캐시가 인스턴스마다 따로 생겨 중복 요청이 나갑니다.
- 단, ④는 설정(최소·최대 인스턴스 1, CPU 항상 할당)으로 풀 수 있습니다. KIS로 바꾸는 근본 이유는 ①②③입니다.

## 3. 향후 구조 (stage6 이후 논의)

| 데이터 | 소스 | 주기 | 방식 |
| --- | --- | --- | --- |
| 전 종목 일일 시세 (분석, 순위, 과거 데이터) | **pykrx** (현행 유지) | 장 마감 후 1일 1회 | 일괄 다운로드 |
| 관심종목 장중 시세 | **KIS REST** | 15분 | Cloud Scheduler → Cloud Run → DB 저장 |
| 클릭한 종목 현재가·상세 | **KIS REST** | 온디맨드 | 클릭 시 바로 조회 |
| (선택) 실시간 차트 | KIS WebSocket | 상세 화면을 보는 동안 | 필요해지면 추가 |

**이렇게 나눈 이유**

- **pykrx를 유지하는 이유:** KIS에는 전 종목 일괄 다운로드 API가 없어서 종목마다 요청해야 합니다(약 2,700종목). pykrx는 요청 1번이면 되고, 하루 1번만 호출하니 차단 위험도 낮습니다.
- **KIS REST를 쓰는 이유:** 공식 API라 IP 차단이 없고 요청 한도가 문서에 명시돼 있습니다. 시세 지연도 1분 이내로 필요에 따라 줄일 수 있습니다
- **WebSocket을 기본으로 쓰지 않는 이유:** 연결과 해제를 반복하는 방식에는 맞지 않고, 체결이 있어야 데이터가 옵니다. 한 번 값을 받는 용도에는 REST가 적합합니다.
- **Cloud Run 설정:** 스케줄러 호출도 일반 요청이라 기본 설정 그대로 동작하고, 요청 사이에는 인스턴스가 쉽니다. 데이터는 DB에 저장되어 인스턴스가 내려가도 남습니다.

**화면 표기:** 관심종목에는 "기준 시각 HH:MM"을 함께 표시합니다.

## 4. 참고 사항

- yfinance 한도는 Yahoo가 공개한 수치가 아니라 흔히 인용되는 값입니다. 실제로는 더 빨리 막힐 수 있습니다.
- KIS 초당 요청 한도(실전 계좌 약 20회, 모의투자 약 2회)는 도입 시점에 공식 문서로 다시 확인해야 합니다.
- KIS를 쓰려면 한국투자증권 계좌 개설과 API 키 발급이 필요합니다 (프로젝트 관리자가 등록 완료)

# Cloud Run 배포 고려사항

## 1. yfinance는 관심종목 외에도 씁니다

KIS 전환은 "국내 관심종목 장중 시세"만 다뤄요. 아래 데이터는 4시간 일괄 갱신에서도 yfinance를 써서, 클라우드 IP 차단(위 ③)에 그대로 걸릴 수 있어요.

| 데이터 | 쓰는 곳 |
| --- | --- |
| 미국 시세 (노출 종목, 비교군 약 450개) | 리스트·상세·매력도 |
| 미국 지수 (S&P·NASDAQ·VIX 등) | 대시보드, 시장 심리 지수(VIX) |
| USD/KRW 환율 | 포트폴리오 원화 환산 |
- 배포 전에 원본 `python -m app.ingest.smoke`를 Cloud Run Job으로 돌려 GCP IP에서 yfinance·pykrx·DART·SEC가 응답하는지 확인해요.
- 막히면 미국 일봉·지수는 KIS 해외주식 API로, 환율은 공식 환율 API(수출입은행·한국은행 ECOS)로 바꿔요.
- pykrx도 공식 API가 아니라 KRX 웹을 로그인해서 읽는 방식이라 같은 확인이 필요해요. 리전은 서울(asia-northeast3)로 둬요.

## 2. 앱 안 백그라운드 작업

| 코드 | 하는 일 | 기본 설정에서 생기는 일 |
| --- | --- | --- |
| `services/scheduler.py` | 5분마다 확인, 4시간 갱신·07:00 비교군 | 요청이 없으면 CPU가 없거나 인스턴스가 0이 되어 실행되지 않음 |
| `services/hydration.py` | 상세를 열면 응답 뒤 스레드에서 수집 | 응답 뒤 CPU가 줄어 "loading"이 오래감. 진행 중·실패 기록이 인스턴스마다 따로 생김 |
- API 서비스를 최소·최대 인스턴스 1, CPU 항상 할당으로 두면 로컬과 똑같이 동작해요. 비용은 인스턴스 1개 상시 실행만큼 늘어요.

## 3. 오래 걸리는 작업: Cloud Scheduler + Cloud Run Job

Cloud Scheduler는 정해진 시각에 "호출만" 해요. 무엇을 호출하느냐에 따라 시간 제한이 달라요.

| Scheduler가 부르는 대상 | 시간 제한 | 맞는 작업 |
| --- | --- | --- |
| Cloud Run 서비스 HTTP 주소 | Scheduler 응답 대기 최대 30분, Cloud Run 요청 최대 60분 | 몇 분 안에 끝나는 평시 갱신(`POST /market/refresh`, 관심종목 15분 시세) |
| Cloud Run Job 실행 | 최대 24시간 (기본값은 10분이라 `--task-timeout`을 늘려요) | 매일 07:00 비교군 갱신(`benchmark`), `migrate` |
- 비교군 갱신은 HTTP 주소가 없고 CLI(`python -m app.ingest benchmark`)만 있어요. Job은 이 CLI를 그대로 실행하므로 코드 변경이 없어요.

### 언제 오래 걸리나

| 시점 | DART 재무를 받는 대상 | 걸리는 시간 |
| --- | --- | --- |
| 최초 가동 | 비교군 한국 약 450개 전부 (약 2,250번) | 가장 오래 걸림(몇십 분) → 아래처럼 개발 PC에서 미리 적재 |
| 평소 매일 07:00 | 재무 유효기간이 지난 종목만 | 짧음. 일봉·밸류에이션은 전 종목 한 번에 받음 |
| 90일 상한 도래 | 종목마다 0~6일 앞당겨 분산 → 하루 약 65개 | 조금 늘어남 |
| 30일 재선정 | 새로 비교군에 들어온 종목만 | 조금 늘어남 |
| 실적 시즌(3월 말~4월 초) | 12월 결산 회사가 사업보고서 공시 즉시 만료 → 약 1주 몰림 | 평소보다 길어짐 |

### 최초 적재는 개발 PC에서

최초 적재 시간은 DB 위치가 아니라 외부 API 한도·간격 때문이에요. 어디서 받아도 같으니 개발 PC에서 미리 받아 두고, Cloud Run은 갱신만 해요.

1. 개발 PC compose DB에 `init-db` → `all` → `benchmark` 적재 (실패해도 로컬에서 다시 실행)
2. `pg_dump`로 떠서 Supabase에 복원
3. Cloud Run은 `DATABASE_URL`만 Supabase로 바꿔 갱신만 담당
- 적재는 배포 직전 1~2주 안에 해요. 일봉은 빠진 날짜만 받아 괜찮지만, 재무는 90일이 지나면 만료돼서 3개월 넘게 벌어지면 첫 갱신 때 거의 다시 받아요.
- Scheduler가 시간 초과로 재시도해도 advisory lock이 중복 실행을 막아요.
- 앱 안 스케줄러와 Scheduler를 같이 쓰면 같은 작업을 두 군데서 부르게 돼요. Scheduler를 쓰면 `SCHEDULER_ENABLED=false`로 꺼요.

## 4. KIS 도입 시

- 접근 토큰은 24시간 유효하고 발급 횟수 제한(약 1분 1회)이 있어요. 인스턴스·콜드 스타트마다 새로 받지 않게 DB에 저장해 함께 써요.
- 15분 시세 수집은 장 시간(09:00~15:30)과 거래일에만 돌려요. 휴장일은 이미 쓰는 `exchange-calendars`로 판단해요.

## 5. 설정 체크리스트

- DB(Supabase): **세션 풀러(포트 5432)**로 연결해요. 트랜잭션 풀러(6543)는 세션 advisory lock을 깨서 중복 실행 방지가 동작하지 않고, 직접 연결 주소는 IPv6 전용이라 Cloud Run에서 바로 붙기 어려워요.
- DB 버전: 로컬은 Postgres 16이에요. 덤프는 같거나 높은 버전에 복원해야 안전해서 Supabase 프로젝트 버전을 확인해요.
- DB 용량: 무료 500MB. 지금 팀 DB는 16MB(146종목)이고, 비교군 약 900개·상장 목록까지 넣으면 수백 MB 안쪽으로 추정해요. 원본 DB를 다 채운 뒤 `pg_database_size`로 확인해요. 7일 미사용 일시정지는 매일 갱신이 있어 해당하지 않아요.
- 포트: CMD가 8000 고정이라 Cloud Run 컨테이너 포트를 8000으로 지정해요.
- 헬스 체크: Dockerfile HEALTHCHECK는 무시돼요. startup probe를 `/health/db`로 걸어요.
- 파일: 격리 CSV(`/srv/data/quarantine`)는 메모리 파일시스템이라 인스턴스가 내려가면 사라져요. smoke 결과 파일은 `docs`가 이미지에 없어 콘솔 로그로 확인해요.
- 비밀값: DART·KRX·KIS 키는 Secret Manager에 둬요.
- 메모리: pandas와 비교군 400일 일봉 때문에 1~2GiB로 둬요.
- 인증: 단일 사용자 데모 모드라 URL이 공개되면 누구나 같은 관심종목·포트폴리오를 바꿀 수 있어요. 시연 기간에만 열거나 IAP로 막아요.
