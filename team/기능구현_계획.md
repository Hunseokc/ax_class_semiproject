# 추가 기능 구현 계획

`04_기능구현_아이디어.md`를 지금 코드와 맞춰 보고 정리한 실행 계획이에요. 이 원본 저장소에서 먼저 구현·검증한 뒤 팀 저장소에 옮겨요.

결정 D1~D10은 2026-10-16에 권하는 답대로 정했어요 (맨 아래 "결정 사항"). 본문은 그 결정을 반영한 내용이에요. D4·D5·D8은 "측정 뒤 정한다"는 방식을 정한 것이라, 수치·방식은 정해진 시점에 이 문서에 채워요.

아이디어 문서에 없거나, 코드와 다르게 적힌 부분이에요. 계획은 이 내용을 반영했어요.

## 1단계. 매력도 안정성 팩터 개편

### 목표

안정성 = 변동성(1년) + **1년 최대 낙폭**. 안정성만 섹터 중립화를 꺼요. 수익성·안정성 설명 문구를 바꿔요.

### 바꾸는 곳

| 파일 | 바꾸는 내용 |
| --- | --- |
| `backend/app/queries/score_metrics.sql` | `base`에 `vm.max_drawdown_1y` 추가, `inp`로 전달. `debt_ratio` 행 → `('max_drawdown', 'safety', c.max_drawdown_1y, NULL, NULL)`. 머리 주석의 z_fixed 설명 수정 |
| `backend/app/queries/score_neutralize.sql` | `g`에 `mv.factor` 추가, `SET z_adj = CASE WHEN s.factor = 'safety' OR s.group_id IS NULL OR s.n = 1 THEN s.z_raw ...` |
| `backend/app/queries/score_zscore.sql` | 주석만 수정 (z_fixed 규칙은 유지) |
| `backend/app/services/scoring.py` | `METRICS`: `"max_drawdown": Metric("safety", "1년 최대 낙폭", +1, "일봉 252개 미만")`. 낙폭은 음수라 값이 클수록(0에 가까울수록) 좋아 방향 +1 |
| `frontend/js/pages/stock.js` | 142행 안정성 설명 → "주가가 덜 출렁이고 덜 빠지는가", 수익성 설명 → "자본과 매출로 돈을 잘 버는가 (최근 연간 기준)", 148행 `debt_ratio` 배수 표기 분기 제거(낙폭은 기본 % 표기, 부호 없이 음수 그대로) |
| `backend/tests/test_scoring.py` | 기대값 계산의 `debt_ratio`(230행), 자본 ≤ 0 고정 검증(256행), z 읽기(321행)를 낙폭 기준으로. **새 테스트 2개**: 안정성은 섹터 중립화가 꺼지는지(`z_adj = z_raw`), 낙폭 NULL 사유가 "일봉 252개 미만"인지 |
| `docs/09_매력도_점수_정의서.md` | 2절 지표 표, 4절 중립화 범위, 7절 프리셋별 순위 재계산 결과, 화면 이름 표 |

바꾸지 않는 것: DB 스키마, 프리셋 가중치, API 응답 모양, 수집 코드, '투자 지표 상세'의 부채비율(`api/analysis.py:39`, `v_stock_metrics.debt_ratio`).

### 검증

1. `pytest backend/tests/test_scoring.py` 통과
2. 개발 DB에서 점수 재계산 후, 아이디어 문서 "바꾸면 이렇게 돼요" 표(TSLA 75 → 41 등)와 값이 같은지 확인
3. 상장 종목 하나를 열어 참고 점수에 안정성이 나오는지 확인
4. 화면 확인은 저장소 밖 Playwright로 상세 화면 안정성 카드만 봐요

배포 직후 점수를 한 번 다시 계산해요. 그 전까지 상장 종목 참고 점수는 낙폭 비교값이 없어 안정성이 빠져 보여요 (0절 #5).

## 2단계. 실적 시즌 부하 분산 (회사 단위 잠금·묶음 저장·하루 재무 예산)

### 목표

상세 요청이 07:00 비교군 갱신 뒤에 줄 서지 않게 하고, 실적 시즌에도 하루 작업량을 일정하게 해요.

### 방식

- **잠금은 외부 호출에만, 회사 단위로**: DART/SEC를 부르는 동안만 잠금을 잡고, 회사 하나가 끝나면 풀어요. 상세 요청은 지금 처리 중인 회사 하나만 기다리면 돼요
- **DB 쓰기는 모아서 한 번에**: 받은 재무·공시 행, `freshness` 기록, `ingestion_logs` 행을 메모리에 모았다가 20개 회사(D3)마다 한 트랜잭션으로 넣어요. 회사 300개면 트랜잭션이 약 900번 → 약 15~30번으로 줄어요
- **잠금 연결은 하나를 재사용**: 세션 잠금은 연결에 묶여 있어서, 회사마다 새 연결을 열지 않고 반복문 동안 연결 하나를 잡아 두고 그 위에서 `pg_advisory_lock`/`unlock`만 반복해요

### 바꾸는 곳

| 파일 | 바꾸는 내용 |
| --- | --- |
| `backend/app/ingest/store.py` | `SEC_LOCK_KEY` 추가. 국가 → 잠금 키 함수 `provider_lock_key(country)`. 연결 하나로 키를 반복 잠그는 `LockSession`(또는 `advisory_lock`에 연결 인자) 추가. 모은 행을 한 트랜잭션에 넣는 `BatchWriter`(테이블별 행·freshness 표시·로그 행을 모아 `flush`) 추가 |
| `backend/app/ingest/jobs.py` | `load_financials`·`load_disclosures`의 묶음 잠금을 없애요. `_load_financials`·`_load_disclosures` 반복문에서 **외부 호출 구간만** 회사 단위 잠금으로 감싸고, 결과는 `BatchWriter`에 넣어요. 반복이 끝나거나 예외가 나도 `finally`에서 남은 것을 flush |
| `backend/app/services/freshness.py` | `mark`를 묶음 트랜잭션 연결 안에서 부를 수 있게 유지. `due(...)`에 `limit`·정렬(유효기간이 가장 오래 지난 순) 인자 추가 |
| `backend/app/ingest/benchmark.py` | `load_benchmark`가 `due_bench`를 하루 예산(`fin_daily_budget`)만큼만 받음. 노출 종목(`due_freq`)은 예산과 무관 |
| `backend/config/universe.yaml` | `ingest.flush_every: 20` (D3 확정), `benchmark.fin_daily_budget: 100` (D4 임시값, 첫 배포 뒤 조정) |
| `backend/app/providers/dart.py` | `_limiter = WindowLimiter(45, 60.0)` — 프로세스 2개(API + Job)가 동시에 돌아도 합계 분당 90번 안에 들게 절반으로 (D2) |
| `backend/app/services/data_quality.py` + 점수 응답 | "재무 기준 FY2025 n개 / FY2024 m개" 표기용 집계를 `data_quality`에 추가 (화면 표기는 3단계 PR에 같이) |

### 묶음 저장에서 지킬 규칙

- **재무 행과 `freshness.mark`는 같은 트랜잭션**에 넣어요. 따로 넣으면 중간에 죽었을 때 "적재 안 됐는데 신선함"으로 표시될 수 있어요
- **실패 로그는 적재와 별도 트랜잭션**으로 써요. 지금 `job_log`가 "적재 롤백 시에도 실패 기록 보존"을 약속하고 있어서, flush가 실패해도 `ingestion_logs`는 남아야 해요. flush가 실패하면 그 묶음 회사들을 FAILED로 다시 기록해요
- **상세 hydrate(회사 1개)는 바로 flush**해요. 화면이 적재 직후 DB를 읽기 때문이에요. 묶음 크기 1이면 지금 동작과 같아요
- 미국 `_load_valuation_base`(기초값 + `derive_us_valuations`)는 재무 저장 뒤에 돌아야 해서 flush 직후 묶음 단위로 실행해요

### 주의할 점

- `WindowLimiter(90, 60.0)`는 프로세스 안에서만 공유돼요. 잠금이 회사 단위가 되면 여러 프로세스(API 서비스 + Cloud Run Job)가 번갈아 DART를 부를 수 있어요. 각자 분당 90번이면 합쳐서 한도를 넘을 수 있어서, **프로세스별 한도를 45로 낮춰요** (D2). DB 기반 카운터는 구현이 커서 프로세스가 3개 이상으로 늘 때 다시 검토해요
- 잠금 대기 시간은 `job_log` 비고에 남겨 상세 요청이 실제로 얼마나 기다리는지 확인해요

### 검증

- 단위 테스트: 잠금 키가 국가별로 나뉘는지, 예산이 `limit`으로 적용되고 노출 종목은 빠지지 않는지, flush 전에 예외가 나면 freshness가 표시되지 않고 실패 로그는 남는지, 묶음 크기 20에서 25개 회사면 flush가 2번인지
- 통합 테스트: 비교군 갱신을 스레드로 돌리는 중에 상세 hydrate가 회사 하나 처리 시간 안에 시작되는지(가짜 provider에 지연을 넣어서)

## 3단계. 시장·섹터 점수 (종목 상세 투자 매력도 카드)

### 목표

종목 상세 '투자 매력도' 카드에서 매력 점수 아래에 **"시장·섹터 점수" 게이지 하나**를 보여줘요(코드·API 이름은 `market_condition`, 화면 이름은 "시장·섹터 점수"). 매력도가 높아도 시장·섹터가 약한 날이면 숫자로 드러나게 하는 위험 표시예요.

- 해설·권유 문구는 넣지 않아요("구매 비권장" 같은 말 없음). 점수와 재료값만 보여줘요
- 홈의 시장 심리 카드는 그대로 두고, 홈 정보를 상세에 다시 늘어놓지 않아요
- 새 외부 호출·새 테이블·새 API가 없어요

### 계산 정의 (D1 확정)

비중·기간은 아래 값으로 시작하고, 배포 한 달 뒤 상세 화면 값 분포를 보고 조정해요.

| 재료 | 값 | 0~100 | 비중 (D1) |
| --- | --- | --- | --- |
| 시장 | 그 종목 국가의 **시장 심리 지수** 최신 저장값 (`market_sentiment_daily`) | 그대로 | 0.7 |
| 섹터 흐름 | 같은 `stocks.sector` 비교군 종목들의 **최근 5거래일 수익률 중앙값** | `clamp(50 + r × 100 × 5)` → −10% 이하 0, 0% 50, +10% 이상 100 | 0.3 |

- 시장·섹터 점수 = 0.7 × 시장 + 0.3 × 섹터 흐름 (정수로 반올림)
- 섹터 흐름 변환은 시장 심리의 이동평균 괴리 점수와 같은 배율(×5)이라 50이 중립인 점이 맞아요
- 섹터가 없거나(`sector` NULL — 금융·매핑 없음) 섹터 표본이 5개 미만이면 섹터를 빼고 시장만 써요. 화면 문장으로 안내 (화면 절 참고)
- 시장 심리 저장값이 기준일보다 5거래일 넘게 오래됐으면 점수 없이 "데이터 부족"
- 기준일 = 그 국가 마지막 마감 거래일. 섹터 중앙값은 그날까지 일봉이 있는 종목만 넣어요
- 라벨은 매력 점수와 같은 구간·단어(`scoreBand` — 낮음 등)를 써서 두 게이지를 같은 눈으로 읽게 해요. 별도 경고 문구는 없어요

### 4-1. 한국 재무: 일괄 첫 적재 + 기준점 증분 갱신

DART에는 "최근 재무"를 바로 주는 API가 없어요. 그래서 **처음엔 파일로 한 번에 넣고, 이후엔 새 공시가 난 회사만 다시 받아요.** 지금 재무는 사업보고서(`reprt_code=11011`)만 쓰므로 증분 대상도 사업보고서와 그 정정 공시예요.

**① 첫 적재 (로컬, API 호출 없음)**

- OpenDART 사이트의 "재무정보 일괄다운로드"(공시정보활용마당)에서 사업보고서 txt 묶음을 받아요. listed 한국 종목 전체, 최근 3~4개 회계연도분이에요 (D10). 적재 뒤 `pg_database_size`를 재서 무료 500MB에 여유가 적으면 연도 수를 줄여요
- `app/ingest/dart_bulk.py`(새 파일)가 txt를 읽어 지금 `fnlttSinglAcntAll` 파싱과 같은 계정 규칙(연결 우선 → 별도)으로 `financials`에 upsert해요. 회사마다 `data_freshness`도 기록해요
- 개발 PC에서 한 번 돌려 DB에 넣어요. 하루 호출 한도와 상관없어서 listed 한국 종목 전체를 한 번에 채울 수 있어요
- 먼저 확인할 것: txt 계정 이름·코드가 API 응답과 같은지 표본 종목 몇 개로 대조해요. 다르면 대응표를 만들어요

**② 매일 증분 (`list.json` 기준점 방식)**

- `providers/dart.py`에 회사 지정 없이 날짜로 공시 목록을 받는 메서드 추가: `bgn_de`·`end_de`, `pblntf_ty=A`, `pblntf_detail_ty=A001`, `sort=date`, `sort_mth=desc`, `page_count=100`
- 기준점 테이블 `ingest_cursor(source PK, last_rcept_no, last_rcept_dt, updated_at)`를 새로 만들어요 (`008_ingest_cursor.sql`)
- 매일 07:00 작업 앞에서:
  1. `bgn_de = last_rcept_dt - 2일`, `end_de = 오늘`로 최신순 페이지를 넘겨요. 겹치게 받는 이유는 늦게 반영되는 공시를 놓치지 않으려는 거예요
  2. `rcept_no <= last_rcept_no`인 행만 남은 페이지가 나오면 멈춰요. 같은 날짜 안의 순서는 보장되지 않으므로 정확히 일치하는 번호를 찾지 말고 크기로 비교해요
  3. 받은 `corp_code` 중 DB에 있는 종목만 골라 재무 유효기간을 끝내요 (`invalidate_on_annual_report`와 같은 방식). 공시 행은 `disclosures`에 upsert해서 중복은 저절로 사라져요
  4. 모두 성공한 뒤에만 `ingest_cursor`를 가장 큰 `rcept_no`로 갱신해요. 중간에 실패하면 다음 실행이 같은 지점부터 이어 받아요
- 정정 공시: `[기재정정]` 사업보고서는 새 `rcept_no`로 올라오므로 위 흐름에 같이 잡혀요. 제목에 "사업보고서"가 들어가는지로 판단하는 지금 조건을 그대로 써요
- 공시 직후엔 재무 API가 아직 비어 있을 수 있어요. 빈 응답이면 `FAILED`로 남기고 다음 날 다시 받아요 (최신으로 기록하지 않아요)
- 기준점이 3개월보다 오래되면(조회 기간 제한) 3개월씩 나눠 받아요

**효과**

- 받아 둔 한국 종목은 회사별 공시 목록 호출이 필요 없어요. 하루 호출은 목록 몇 페이지 + 새로 공시한 회사 수만큼이에요

- KIS 관심종목 장중 시세는 4단계와 독립이에요. 접근 토큰 DB 저장, 장 시간·거래일 판단(`market_calendar`)을 재사용해요
