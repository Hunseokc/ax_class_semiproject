# 매력도 모델 전면 재검토 요청 (레드팀 모드)

## 0. 너의 역할과 태도 — 가장 중요

너는 이 매력도 모델을 만든 사람이 아니라, **이 모델이 틀렸다는 것을 증명하러 온 외부 감사인**이다.

- 기본 가정은 "이 모델은 잘못 설계됐다"이다. 반증 증거가 있을 때만 "문제없음"이라고 쓴다.
- **방어 금지.** 아래 표현은 반론의 근거로 쓸 수 없다.
  - "설계 의도대로 동작한다" / "원본과 같다" / "문서에 그렇게 정했다" / "프리셋 설명이 ~이므로 맞다"
  - 설계 문서(`개발산출물/09_매력도_점수_정의서.md`)와 과거 결정(`backup_team_1차/기능구현_아이디어.md` 등)도 **검토 대상**이지, 판정 기준이 아니다.
- 모든 주장은 **실제 DB 조회 결과나 코드 줄 번호**로 뒷받침한다. 확인하지 못한 것은 "확인 못함"이라고 쓰고 추측으로 메우지 않는다.
- "문제가 아니다"라고 판정하려면, 그 판정을 뒤집을 수 있는 반례를 최소 1개 찾아 시도한 기록을 함께 남긴다.
- 문제를 찾으면 축소하지 않는다. 심각도는 "투자자가 이 점수를 믿고 행동했을 때 얼마나 잘못된 판단을 하게 되는가"로 매긴다.

데이터 → 지표 → 정규화 → 중립화 → 팩터 → 프리셋 합산 → 0~100 변환 → 화면 표현까지, 전 단계를 본다.

| 단계 | 파일 |
|---|---|
| 유니버스·테마·family | `backend/config/universe.yaml`, `backend/db/views.sql`(`v_stock_theme`, `v_stock_metrics`) |
| 지표 원값 | `backend/app/queries/score_metrics.sql`, `backend/app/services/scoring.py`(`METRICS`) |
| 로버스트 Z·클리핑 | `backend/app/queries/score_zscore.sql` |
| 섹터 중립화 | `backend/app/queries/score_neutralize.sql` |
| 팩터·종합·Φ 변환 | `backend/app/queries/score_aggregate.sql` |

## 3. 공격 관점 — 아래 질문 전부에 데이터로 답할 것

### A. 지표 하나하나의 경제적 의미
- 각 지표가 "지금 싸다 / 돈을 잘 번다 / 성장한다 / 안전하다 / 추세가 좋다"를 정말 재는가, 아니면 다른 것(회계 일회성, 주가 수준, 업종 구조)을 재는가?
- 일회성 손익, 영업권 손상, 자본 음수, 적자 → 흑자 전환, 결산월 차이, 회계기준(K-IFRS vs US GAAP) 차이에 각 지표가 어떻게 반응하는가?
- 분모·분자에 주가가 들어가는 지표끼리 같은 정보를 중복으로 세고 있지 않은가? (지표 간 상관 행렬로 확인)

### B. 정규화·중립화·합산의 수학
- 클리핑(±3), MAD 대체 규칙, 축소 계수 k = 5, family 분리, 국가 분리가 순위를 어떻게 왜곡하는가?
- 팩터 = 지표 평균 → 지표 수가 다른 팩터끼리 분산이 달라 실효 가중치가 바뀌지 않는가? (프리셋마다 실효 가중치 측정)
- 유효 팩터 3개 이상이면 재정규화하는 규칙이 데이터 부족 종목을 유리하게 만드는가? (#12 검증)
- 종합 점수를 다시 표준화하고 Φ로 변환하는 방식이 사용자에게 주는 의미가 정직한가?

### C. 프리셋 설계
- 4개 프리셋(위험·성장·균형·가치)의 가중치가 실제 투자 스타일과 맞는가? 공개된 팩터 모델(Fama-French, AQR Quality Minus Junk, Greenblatt 마법공식, Piotroski F-Score 등)과 비교해서 무엇이 빠졌는가?
- 각 프리셋 상위 10개를 뽑아서, 투자 상식으로 이상한 종목이 몇 개인지 세고 이유를 적는다.
- 프리셋 이름("가치", "성장")이 약속하는 것과 실제 상위 종목이 일치하는가?

### D. 반례 사냥 (sanity case)
아래 유형을 DB에서 실제로 찾아 점수가 상식과 어긋나는지 본다.
- 가치 함정: 매출 다년 감소 + 저PER
- 일회성 손익: 순이익 ≫ 영업이익, 또는 전년 대규모 손상
- 업황 정점: 최신 이익이 3년 평균의 2배 이상
- 비주식·특수 구조: ETF·신탁·리츠·지주사·금융
- 데이터 부족: 유효 팩터 3~4개, 일봉 부족
- 반대 방향: 상식적으로 우량한데 점수가 낮은 종목

### E. 민감도·안정성
- 가중치를 ±0.1 흔들거나 지표 하나를 빼면 상위 10이 얼마나 바뀌는가? (순위 상관, 상위 10 교집합)
- 하루하루 점수가 얼마나 출렁이는가? (as_of가 여러 날 있으면)
- 데이터 한계 때문에 수익률 백테스트가 불가능하면 불가능하다고 명시하고, 가능한 범위(예: 1년 일봉으로 점수 상위·하위의 사후 수익률 비교)를 제시한다.

### F. 표현과 신뢰
- 99점, "매력도 순위"라는 표현이 사용자에게 무엇을 약속하는가? 모델이 실제로 그것을 줄 수 있는가?
- 화면에서 점수의 근거(팩터 기여, 일회성 경고, 데이터 부족)가 충분히 보이는가?

## 4. 진행 방식

1. **읽기 전용.** 코드와 DB를 고치지 않는다. 조회 SQL은 개발 DB에서 직접 실행한다(`docker compose exec -T db psql -U stock -d stockdb`).
2. 1단계: 코드와 09 문서를 읽고 모델의 **암묵적 가정 목록**을 먼저 만든다. (예: "순이익은 반복 가능한 이익이다", "장부가는 청산가치에 가깝다")
3. 2단계: 각 가정을 3절 관점으로 공격하고, 깨지는 가정마다 DB 반례를 붙인다.
4. 3단계: 2절의 기존 문제도 재검증한다. 내가 틀렸거나 과장한 것이 있으면 그것도 지적한다.
5. 4단계: **판정** — "부분 수리로 충분한가, 재설계가 필요한가"를 근거와 함께 하나로 정한다.

## 5. 결과물 형식

1. **한 줄 판정**: 수리 / 재설계 중 하나, 그리고 이유 한 줄
2. **문제 목록** (심각도 순): 번호 · 문제 · 근거(SQL 결과 또는 파일:줄) · 영향받는 프리셋·종목 · 심각도(치명/높음/중간/낮음)
3. **깨진 가정 목록**: 가정 · 반례
4. **"문제없음" 판정 목록**: 항목 · 시도한 반례 · 왜 버텼는지
5. **추천**: 문제마다 가장 좋은 해결 하나. 재설계라면 새 모델의 뼈대(팩터·지표·합산 방식)를 제안하고, 지금 모델보다 나아지는 점을 같은 반례로 보여준다.
6. **확인 못한 것**: 데이터·시간 한계로 검증하지 못한 항목

선택지를 늘어놓지 말고, 각 항목에 가장 좋은 답 하나를 쓴다. 보고서를 다 쓰기 전에는 중간에 "진행할까요?"로 멈추지 말고 끝까지 간다.
