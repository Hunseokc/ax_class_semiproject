# StockMind 컨센서스·애널리스트 의견 데이터 소스 검토 요청서

Oct 28, 2026 · @더덕

## 1. 배경과 검토 목적

이번 작업은 **코드 구현이 아니라 검토 보고서 작성**이다. 목표는 아래 무료 데이터 소스로 StockMind 매력도 모델에 필요한 컨센서스와 애널리스트 의견을 얼마나 얻을 수 있는지 판정하는 것이다.

- 이전 결론은 "개인 프로젝트에서 무료 API로 컨센서스 수집은 어렵다"였다. 이 결론을 재검증한다.
- 매력도 모델의 성장성 팩터는 가이던스·컨센서스 사용을 전제로 설계되었다. 현재 계획은 국내 = 한경 컨센서스 크롤링, 해외 = 무료 출처(단일 추정이라도)이다.
- 추가로 애널리스트 투자의견을 받을 수 있는지, 받는다면 어떤 형태(개수 집계 / 문장)인지 확인한다. 형태에 따라 활용 방침이 달라진다(4장).

검토 결과는 각 항목에 대해 **사용 가능 / 제한적 사용 / 사용 불가** 중 하나로 판정하고, 근거를 실제 응답으로 제시한다. 문서나 블로그 설명만으로 판정하지 않는다.

**범위 결정 (확정, 검토 대상 아님)**

| 데이터 | 매력도 점수 | 화면 활용 |
| --- | --- | --- |
| 컨센서스 EPS·매출 추정, 추정 성장률 | 반영하지 않는다 | 종목 상세에 단순 나열하는 여러 지표 중 하나로만 둔다. 해석·강조하지 않는다 |
| 추정치 리비전 | 반영하지 않는다 | 표시하지 않고 스냅샷만 쌓는다. 후보 팩터로 장부에 열린 이슈로만 남긴다 |
| 애널리스트 투자의견·목표가 | 반영하지 않는다 | 매력도 표시 옆에 별도 라벨의 작은 신호로 표현한다. 기준은 4장 A에서 상세 검토한다 |

근거: 컨센서스 성장률 수준은 이후 수익률과 오히려 역의 관계라는 연구(La Porta 1996, Bordalo 외 2019)가 있어, 점수에 넣거나 해석을 붙이면 만드는 쪽과 보는 쪽 모두 판단이 어려워진다. 진행 중인 매력도 sanity 루프에는 이번 데이터를 넣지 않는다.

## 2. 검토 대상 데이터 소스

해외는 yfinance, 국내는 한국투자증권(KIS) Open API를 검토한다. KIS는 pykrx 대체용으로 이미 프로젝트에 연동되어 있으므로 기존 인증 설정을 재사용한다.

| 구분 | 대상 | 기대하는 내용 | 확인이 필요한 점 |
| --- | --- | --- | --- |
| 해외 | yfinance `earnings_estimate` | 기간별(이번·다음 분기, 올해·내년) EPS 추정 avg/low/high/애널리스트 수/성장률 | 지표 목록에 표시할 값으로 쓸 수 있는지(점수 미반영) |
| 해외 | yfinance `revenue_estimate` | 기간별 매출 추정 컨센서스 | 위와 동일 |
| 해외 | yfinance `eps_trend`, `eps_revisions` | EPS 추정치의 7·30·60·90일 전 대비 변화, 상향·하향 횟수 | 스냅샷 축적 대상으로 적합한지(점수 미반영) |
| 해외 | yfinance `growth_estimates` | 종목·업종·지수 대비 성장률 추정 | 업종 대비 상대 평가에 쓸 수 있는지 |
| 해외 | yfinance `get_earnings_dates(limit)` | 분기별 실적발표일, EPS 예상치·실제치·서프라이즈 | 어닝 서프라이즈 이력 확보 가능 여부 |
| 해외 | yfinance `get_recommendations()` | 월별 strongBuy/buy/hold/sell/strongSell 애널리스트 수 | 카운트형 의견 (4장 A) |
| 해외 | yfinance `analyst_price_targets` | 목표가 current/low/high/mean/median | 목표가 괴리율 계산 가능 여부 |
| 해외 | yfinance `upgrades_downgrades` | 증권사별 등급 변경 이력(날짜·회사·이전/이후 등급·목표가) | 카운트형인지 문장형인지 (4장) |
| 국내 | KIS 국내주식 종목추정실적 `/uapi/domestic-stock/v1/quotations/estimate-perform` | 연도별 추정 매출·영업이익·순이익·EPS·PER 등 | **시장 컨센서스인지, 한국투자증권 단일 하우스 추정인지**, 커버 종목 범위 |
| 국내 | KIS 국내주식 종목투자의견 `/uapi/domestic-stock/v1/quotations/invest-opinion` | 한 종목에 대한 여러 증권사의 의견·목표가 이력 | 직접 집계해 목표가 컨센서스를 만들 수 있는지, 문장형 필드가 있는지 |
| 국내 | KIS 국내주식 증권사별 투자의견 `/uapi/domestic-stock/v1/quotations/invest-opbysec` | 특정 증권사가 낸 여러 종목의 의견 | 종목 단위 분석에 보조적으로라도 필요한지 |
| 비교 기준 | 한경 컨센서스 (기존 크롤링 계획) | 국내 시장 컨센서스 기준값 | KIS 값이 컨센서스인지 판별하는 비교 대상으로만 사용 |

참고 자료: [yfinance 정리 블로그](https://whdrns2013.github.io/python/20260129_001_yfinance/), [KIS API 포털 - 종목추정실적](https://apiportal.koreainvestment.com/apiservice-apiservice?/uapi/domestic-stock/v1/quotations/estimate-perform). KIS 포털과 [공식 예제 저장소(open-trading-api)](https://github.com/koreainvestment/open-trading-api)에서 TR ID와 요청·응답 필드를 직접 확인한다.

## 3. 검토 항목과 판정 기준

표본 종목에 실제로 호출해 보고, 다음 다섯 가지를 소스별로 확인한다.

**표본 종목** (시총·커버리지 차이를 보기 위해 섞는다)

- 국내: 대형주 3개(삼성전자 005930, SK하이닉스 000660, 현대차 005380), 중형주 2개, 코스닥 소형주 2개. 프로젝트의 항상 캐싱 대상(거래량 상위) 종목이 있으면 그중에서 고른다.
- 해외: M7 중 2개(AAPL, NVDA), 미국 중형주 2개, 그리고 yfinance의 국내 티커 지원 수준을 보기 위한 `005930.KS`.

**확인 항목**

1. **커버리지**: 표본 종목 중 값이 채워져 나오는 비율. 빈 값, None, 빈 DataFrame, 오류를 구분해서 기록한다.
2. **컨센서스 여부**: 여러 애널리스트의 평균인지, 단일 추정인지. 특히 KIS `estimate-perform`은 한경 컨센서스 값과 대형주 2\~3개를 비교해 판별한다. 추정 기관 수 같은 필드가 있는지도 확인한다.
3. **응답 필드**: 실제 응답의 필드명, 의미, 단위(원/억원/%, USD/KRW), 기준 기간(회계연도, 분기). KIS는 TR ID와 output1\~N 구조를 포함한다.
4. **갱신 주기와 이력**: 값이 얼마나 자주 바뀌는지, 과거 시점의 값을 조회할 수 있는지(리비전 모멘텀 계산에 필요).
5. **제약**: 호출 제한(초당/일당), 모의투자 도메인에서 동작 여부, 클라우드 배포 환경에서의 차단 가능성, 약관상 재배포·표시 제한.

**판정 기준**

| 판정 | 기준 |
| --- | --- |
| 사용 가능 | 표본의 대부분에서 값이 나오고, 의미와 단위가 명확하며, 매력도 모델의 팩터에 바로 넣을 수 있다 |
| 제한적 사용 | 대형주만 커버되거나, 단일 추정이거나, 직접 집계가 필요하다. 어떤 조건에서 쓸지, 값이 없을 때 어떻게 처리할지 함께 제안한다 |
| 사용 불가 | 대부분 비어 있거나, 의미가 불분명하거나, 약관·호출 제한상 쓸 수 없다 |

컨센서스는 점수에 쓰지 않으므로 단일 추정이어도 표시할 수 있다. 단, 국내와 해외의 입력 성격이 다르면(컨센서스 vs 단일 증권사) 화면 라벨에서 어떻게 구분할지 제안한다.

## 4. 애널리스트 의견: 데이터 타입별 활용 방침

애널리스트 의견은 받을 수 있다면 사용한다. 다만 활용 방식은 데이터가 어떤 형태로 오는지에 따라 정해진다. 각 소스가 아래 세 유형 중 어디에 해당하는지 판정하고, 유형별 방침에 맞춰 검토한다.

| 유형 | 데이터 형태 | 후보 소스 | 활용 방침 |
| --- | --- | --- | --- |
| A. 카운트형 | 매수·보유·매도 의견 개수 집계 | yfinance `get_recommendations()`, KIS `invest-opinion` 집계 결과 | **시장 상대 기준의 작은 신호로 표기**하는 데만 사용한다 |
| B. 이력형 | 증권사·날짜·의견·목표가가 담긴 표 형태의 건별 데이터 | KIS `invest-opinion`, yfinance `upgrades_downgrades` | 목표가 컨센서스 직접 집계, 상향·하향 추이. 카운트형 신호의 원천으로도 쓴다 |
| C. 문장형 | 의견 근거가 문장으로 있는 데이터(리포트 제목, 코멘트, 요약) | 아직 확인된 소스 없음. 위 소스 응답에 텍스트 필드가 있는지 확인 | **AI API 활용 여부를 검토**한다 |

### A. 애널리스트 의견 신호 (점수 미반영, 작은 별도 표시) — 상세 검토

결정된 원칙은 세 가지다: **시장 상대 기준**, **수준보다 변화 우선**, **최소 건수 미달 시 판단 안 함**. 국내는 매수 의견이 대부분이라 "매수 비율이 높다"는 신호가 아니라 기본값이기 때문이다. 구체적인 기준과 임계값은 정해져 있지 않다. 아래 항목을 **실제 데이터 분포로 잴 뒤** 제안하고, 추측으로 정한 값은 "추측"이라고 표시한다.

#### A-1. 기준 데이터 정의 (A-2·A-3 공통)

- **집계 단위**: 증권사별 최신 1건. B(목표가 집계)와 같은 규칙을 공유한다.
- **집계 기간 후보**: 3·6·12개월. 기간별로 의견이 있는 종목 수와 종목당 의견 수 분포를 비교한다.
- **의견 표기 정규화**: 증권사마다 다른 표기(매수, Buy, Strong Buy, 매수유지, Trading Buy, 중립, Hold, Marketperform, Not Rated 등)를 **매수 / 중립 / 매도 / 미평가** 4단계로 매핑하는 표를 만든다. 표본에서 실제로 나온 표기를 전부 모으고, 매핑이 애매한 표기는 따로 적는다. 미국 등급(Overweight, Outperform, Equal-Weight 등)도 같은 4단계로 맞춘다.
- **소스 일치**: 미국은 yfinance `get_recommendations()`(월별 집계)와 `upgrades_downgrades`로 직접 집계한 값이 맞는지 확인한다. 다르면 어느 쪽을 기준으로 할지 제안한다.

#### A-2. 시장 상대 기준

1. **분포부터 잰다.** 국내·미국 따로, 종목당 매수 비율의 평균·중앙값·백분위(10/25/75/90), 중립·매도가 1건 이상 있는 종목 비율, 종목당 의견 수 분포.
2. **후보 방식을 같은 표본에 적용해 비교한다.**
   - (가) 시장 안 매수 비율 백분위 (상·하위 x%)
   - (나) 비매수(중립+매도) 의견 존재 여부와 건수 — 국내에서 특히
   - (다) 평균 의견 점수(매수=1 … 매도=3)의 시장 안 백분위
   - (라) 건수가 적은 종목의 비율을 시장 평균 쪽으로 당긴 뒤(베이지안 축소) 백분위 — 의견 2건짜리와 30건짜리를 같은 저울에 올리지 않기 위함
3. **방식마다 잴 것**
   - 신호가 붙는 종목 수와 비율. 너무 많으면 변별력이 없다. 적절한 범위를 근거와 함께 제안한다.
   - 시총·의견 수와의 상관. 대형주에만 붙거나 소형주에만 붙으면 적는다.
   - 시점 간 안정성. 한 달 간격 두 시점에서 신호가 뒤집히는 종목 비율.
   - 대표 종목 10개 정도에 실제로 붙는 신호가 상식적으로 말이 되는지.
4. **비교 기준 묶음**: 같은 시장 전체로 할지, 같은 테마 안으로 할지. 테마는 표본이 작아 가능한지부터 확인한다.
5. **산출**: 채택 방식, 임계값 초안, 임계값이 분포의 어느 지점인지, 탈락시킨 방식과 이유.

#### A-3. 변화 우선

1. **변화 이벤트 정의**: 의견 상향·하향(4단계 기준 이동), 목표가 상향·하향, 신규 커버, 커버 중단. 커버 중단이 사실상 부정 신호로 볼 수 있는지, 데이터로 구분되는지 확인한다.
2. **데이터로 가능한지**: KIS `invest-opinion`이 증권사별 직전 의견·직전 목표가를 주는지, 아니면 연속 이력에서 직접 비교해야 하는지. yfinance `upgrades_downgrades`의 구분 필드(상향·하향·유지·신규 등)와 목표가 필드가 있는지.
3. **집계 창과 형태**: 최근 30·60·90일 각각에 대해 상향−하향 순건수, 하향 비율, 여러 증권사 목표가 변화율의 중앙값을 계산해 비교한다. 목표가는 같은 증권사의 직전 대비로만 비교한다.
4. **시장 전체 일괄 조정 구분**: 실적 시즌이나 지수 급락 뒤에는 많은 종목의 목표가가 함께 내려간다. 변화 신호도 시장 평균 대비(A-2와 같은 상대 기준)로 볼지, 절대 건수로 볼지 두 방식을 같은 기간에 적용해 비교한다.
5. **수준과 변화가 충돌할 때**: 예를 들어 매수 비율은 높은데 최근 하향이 남에서 하나의 표시로 합칠지, 변화만 보여줄지, 둘 다 보여줄지 안을 낸다. 기본 방향은 변화 우선이다.
6. **변화 이력이 없을 때**: 데이터가 쌓이기 전(스냅샷 없음)에는 어떻게 표시할지. 소스가 과거 이력을 주면 처음부터 가능하고, 아니면 스냅샷 비교가 필요하다.
7. **근거 확인**: Womack(1996), Jegadeesh 외(2004)의 원문에서 변화·수준의 정의와 결과를 확인하고, 근거 정렬표와 같은 형식(A/B/C)으로 등급을 제안한다. 점수에 쓰지 않더라도 화면 문구의 근거로 쓴다. 미국 연구 결과를 국내에 그대로 적용할 수 없다는 점도 적는다.

#### A-4. 최소 건수와 표시

- 최소 의견 수 후보(2·3·5건)별로 신호 대상 종목 수를 비교한다. 미달이면 "의견 적음"으로만 표시한다.
- 표시 문구 초안 2\~3개. 예: `애널리스트 의견 · 하향 우세 (90일: 하향 3, 상향 0) · 10/27 기준`.
- 점수와 혼동되지 않는 위치·라벨·크기. "매수 추천"처럼 판단을 대신하는 표현은 쓰지 않고, 사실만 적는다.
- 매력도 순위와 의견 신호가 반대일 때(상위인데 하향 우세) 화면에서 어떻게 보일지 예시 종목으로 확인한다.

#### A-5. sanity 연계

- 점수 미반영이므로 기존 required 테스트에 영향이 없어야 한다. 이를 확인하는 규칙을 제안한다(예: 의견 데이터 유무와 무관하게 점수가 같다).
- 신호 규칙용 회귀 케이스 후보를 제안한다. 예: 중립·매도 의견이 있는 국내 대형주, 의견 1건뿐인 종목, 실적 시즌 일괄 목표가 하향 구간.
- 케이스는 `sanity_cases.yaml`에 바로 넣지 않고 제안 목록으로만 보고서에 적는다.

### B. 이력형 → 목표가 컨센서스 직접 집계

- 집계 규칙을 제안한다: 기간(3개월/6개월), 증권사별 최신 1건, 평균과 중앙값 중 무엇을 쓸지, 목표가 미제시("Not Rated" 등) 처리.
- 결과로 현재가 대비 목표가 괴리율과 최근 상향·하향 건수를 만들 수 있는지 확인한다.

### C. 문장형 → AI API 활용 여부 검토

- 먼저 위 소스 중 문장 필드(리포트 제목, 코멘트 등)가 실제로 있는지 확인한다. 없으면 "무료 API 범위에서 문장형 없음"으로 명시한다.
- 없을 경우 다른 후보(예: 리서치 리포트 목록의 제목)는 후보로만 적는다. 크롤링이 필요하면 약관 리스크를 함께 적고 구현은 하지 않는다.
- 문장형이 있다면 AI API 활용을 다음 관점에서 검토한다.
  - 용도: 종목별 의견 근거 요약, 긍정·부정 논거 분류, 보고서 기능의 입력
  - 비용: 종목당 호출 수와 토큰 추정, 캐시 주기(의견은 자주 안 바뀜)
  - 위치: 현재 프로젝트에서 AI 기능은 "예정"으로 분류되어 있다. 당장 구현하지 않고, 어떤 테이블·흐름으로 들어갈지만 제안한다
  - AI 없이도 되는지: 키워드 규칙으로 충분한 수준이면 그쪽을 권고한다

## 5. 제약사항

- **프로젝트 코드는 수정하지 않는다.** 서비스 코드, DB 스키마, 마이그레이션을 바꾸지 않는다. 검증용 호출은 저장소 밖 임시 스크립트나 REPL에서만 하고, 커밋하지 않는다.
- **호출은 최소한으로** 한다. 표본 종목 × API당 1회가 원칙이고, KIS 초당 호출 제한을 지킨다. 반복 테스트가 필요하면 처음 응답을 로컬 파일로 저장해 재사용한다.
- **인증 정보는 기존 환경변수를 쓴다.** 키·토큰 값을 보고서나 로그에 출력하지 않는다. 실전/모의 도메인 중 어느 쪽으로 호출했는지는 기록한다.
- **운영 설계는 기존 원칙을 따른다.** 외부 API 호출 최소화, DB 저장 후 재사용. 컨센서스·의견 데이터는 일 1회 또는 주 1회 갱신으로 충분한지 판단한다.
- **문서나 기억에 의존한 단정을 하지 않는다.** 확인하지 못한 항목은 "미확인"으로 남기고, 왜 확인하지 못했는지 적는다.
- **약관 리스크를 적는다.** yfinance는 비공식 라이브러리이고, KIS 시세 데이터도 이용 조건이 있다. 과제 발표·데모와 공개 서비스에서 달라지는 점이 있다면 구분한다.

## 6. 수집·갱신 운영과 변화 감지

수집은 웹앱과 분리하고, 갱신은 고정 주기가 아니라 **변화 신호로 고른 종목만 다시 호출**하는 방식을 전제로 검토한다. 컨센서스와 의견은 리포트 발간·실적 발표 같은 사건이 있을 때만 바뀌기 때문이다. API 호출량도 비용으로 본다.

**전제 구조**

- 수집 스크립트는 웹앱과 별도로 두고, 초기 적재는 개발용 로컬 PC에서 실행해 Cloud DB에 직접 쓴다. Cloud Run 서비스에서 장시간 배치를 돌리지 않는다.
- 웹앱은 DB만 읽는다. 모든 행에 `fetched_at`을 저장하고 화면에 기준일을 작게 표시한다.
- DB에 없는 종목만 요청 시 1건 가져와 캐시한다.
- 이후 상시 운영이 필요하면 갱신 작업을 Cloud Run Jobs + Cloud Scheduler로 옮기는 것을 전제로, 두 환경에서 같은 스크립트가 돌 수 있는지 확인한다. GitHub Actions는 팀 프로젝트의 CI/CD 제약 때문에 제외한다.

**변화 감지 신호 (검토 대상)**

| 신호 | 예상 하루 호출 | 감지 범위 | 확인할 점 |
| --- | --- | --- | --- |
| KIS `invest-opbysec` 증권사별 조회 | 증권사 수만큼(약 30건) | 국내 신규 의견·목표가가 나온 종목 전체 | 날짜 범위 조회 가능 여부, 증권사 코드 목록 출처, 한 번에 반환되는 최대 건수와 페이징 |
| DART 공시검색 (날짜 기준 전 종목) | 몇 건 | 잠정실적·영업실적 공시가 나온 종목 | 공시 유형 필터 방법, 일일 호출 한도 |
| SEC EDGAR 일별 공시 목록 (8-K 실적) | 몇 건 | 해외 실적 발표 종목 | 기존 EDGAR 연동 코드에서 재사용 가능한지 |
| 저장해 둔 실적 발표일 (`get_earnings_dates`) | 0건 (기존 데이터) | 발표일 전후 재조회 대상 | 발표일 정확도, 전후 며칠을 볼지 |
| 시세 이상치 (거래량 급증·급등락) | 0건 (기존 시세 수집) | 리포트·뉴스 가능성이 높은 종목 | 우선순위 가산에만 쓸 수 있는지 |

**신호가 없는 부분 → 예산 기반 갱신**

- 해외 개별 종목의 의견 변경처럼 시장 전체 피드가 없는 데이터는 하루 호출 예산을 정해 두고, "경과 일수 × 중요도(관심종목 등록 수, 인기 종목 여부)"가 높은 순서로 갱신하는 방식을 검토한다.
- 사용자가 상세 화면을 열었을 때 값이 오래됐다면 그때의 1건 갱신도 같은 예산에서 차감한다.
- 안전망으로 월 1회 전체 수집을 둔다. 놓친 변화는 여기서 따라잡는다.
- 해시 비교(값이 같으면 저장 안 함)는 DB 쓰기만 줄이고 API 호출은 줄이지 못한다. 호출 절감 수단으로 제안하지 않는다.

**이 장에서 계산·제안할 것**

1. 실제 호출 제한(KIS 초당 제한, yfinance 차단 경향, DART 일일 한도)과 커버 종목 수를 근거로 한 초기 적재 소요 시간
2. 위 신호를 쓸 때의 평상시 하루 호출 수 추정치
3. 신호별 채택 여부와 우선순위, 감지 누락이 생기는 경우
4. 갱신 대기열 테이블과 `fetched_at` 등 필요한 컬럼 초안 (구현은 하지 않는다)

## 7. 산출물 형식

검토 결과는 `docs/review/consensus-data-review.md` 하나로 작성한다. 다음 순서를 따른다.

1. **결론 요약** (5줄 이내): 이전 결론이 맞았는지, 국내·해외 각각 컨센서스 지표와 애널리스트 의견 신호를 무엇으로 채울지.
2. **소스별 판정표**: 아래 열을 갖춘다.
3. **애널리스트 의견 유형 분류**: 각 소스가 A/B/C 중 어디인지, 각 유형의 활용 제안(신호 규칙 초안, 집계 규칙, AI API 검토 결과).
4. **화면 표시와 스냅샷 제안**: 지표 목록에 넣을 컨센서스 필드와 라벨, 값이 없을 때 처리, 리비전 스냅샷으로 저장할 필드. 애널리스트 의견 신호는 4장 A-2\~A-5의 검토 결과(채택 방식, 임계값 초안, 근거 등급, 표시 문구, sanity 규칙 후보)를 별도 소절로 정리한다.
5. **저장·갱신 설계 제안**: 필요한 테이블 초안, 6장의 변화 감지 신호 채택안과 하루 호출량 추정. 구현은 하지 않는다.
6. **미확인 항목과 질문**: 내가 결정해야 하는 것.
7. **부록**: 표본별 실제 응답 발췌(필드명과 값 몇 개).

**소스별 판정표 열**

| 소스 | 판정 | 커버리지(국내/해외 표본 중 값 있는 수) | 컨센서스 vs 단일 추정 | 주요 필드·단위 | 의견 유형(A/B/C/해당 없음) | 제약·리스크 | 근거 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| (예) KIS estimate-perform | 제한적 사용 | 4/7 | 단일(한투) | 매출액 등, 억원 | 해당 없음 | 커버 종목 제한 | 삼성전자 EPS가 한경 컨센서스와 다름 |

예시 행의 값은 형식 설명용이며, 실제 값으로 바꾸거나 지운다. 작업이 끝나면 결론 요약만 대화창에 다시 보고한다.
