# StockMind 2차 프로젝트 고도화 아이디어

Oct 23, 2026 · @더덕

## 개요

2차 프로젝트는 1차의 "같은 기준으로 비교하는 대시보드"를 "유명 투자자 관점으로 판단을 돕는 도구"로 넓히는 것이 핵심이다. 이 문서는 요구사항 정의 전 단계의 아이디어 정리이며, 확정 사항이 아니다.

**1차 결과물 현황 (2026-10-22 코드 기준)**

| 구분 | 현재 상태 | 2차와 관련된 점 |
| --- | --- | --- |
| 백엔드 | FastAPI · SQLAlchemy 2.x · 원문 SQL, 테스트 507개 | 조회 API는 DB만 읽는 원칙 유지 |
| DB | PostgreSQL 16, 테이블 25 · VIEW 3 · 마이그레이션 001\~010 | 배포는 이미 Supabase PostgreSQL (연결 한도 15) |
| 수집 | pykrx · yfinance · OpenDART · SEC EDGAR, 국내 대체 경로 KIS | SEC 수집 경로(`providers/sec.py`) 재사용 가능 |
| 갱신 | 앱 내 스케줄러 + Cloud Run Jobs 3개, 시세 1시간 TTL | 준실시간 가격은 별도 주기 필요 |
| 프론트 | 바닐라 JS (ES Modules) · Chart.js | React 전환 대상 |
| 사용자 | 로그인 없음, 서명 쿠키 기반 브라우저별 게스트 | `get_current_user_id()` 한 곳만 교체하면 JWT 전환 가능 |
| 분석 | 규칙 기반 매력도(성향별 다중 팩터), LLM 미사용 | 매력도 팩터·`data_quality` JSON을 투자자 모델·AI 입력으로 재사용 |

1차 회고에서 남긴 과제(분기 재무, 투자 스타일 체크리스트, 시나리오 API, KIS 운영 전환, 설정의 사용자별 저장)는 2차 기능과 겹치는 부분이 많아 함께 검토한다.

## 1. 13F 기반 대형 투자자 포트폴리오

분기마다 공개되는 SEC 13F 보유 내역을 받아, 유명 운용사가 무엇을 들고 있고 지난 분기 대비 무엇을 바꿨는지 보여 준다. 2번(모델링)과 7번(포트폴리오 가져오기)의 원천 데이터다.

**보여 줄 것**

- 투자자 목록: 운용사별 총 보유액, 종목 수, 상위 10개 비중, 최근 공시일
- 투자자 상세: 섹터 비중, 분기별 변화(신규 · 추가 · 축소 · 전량 매도), 보유 기간, 회전율
- 종목 상세 위젯: "이 종목을 가진 유명 투자자" (AAPL을 보유한 운용사와 비중·변화)
- 콘센서스: 여러 운용사가 같은 분기에 동시에 산 종목

**데이터 수집**

- 원천: [Form 13F 데이터셋](https://www.sec.gov/data-research/sec-markets-data/form-13f-data-sets) (분기별 ZIP, 2013년 7월부터) 또는 EDGAR에서 운용사 CIK별 13F-HR 원본(infotable XML). 소수의 운용사만 보면 CIK별 수집이 가볍다.
- 기존 `providers/sec.py`의 User-Agent·호출 제한 처리와 `ingest/` 멱등 적재 패턴을 그대로 쓸 수 있다.
- 종목 식별은 CUSIP이다. 티커로 바꾸는 매핑(OpenFIGI 등)이 필요하고, 우리 `stocks`에 없는 종목은 이름만 보여 주거나 상세 수집을 예약한다.
- 테이블 초안: `investors`(CIK, 표시 이름, 스타일 태그) · `filings_13f`(분기, 공시일, 접수번호) · `holdings_13f`(CUSIP, stock\_id, 주식 수, 평가액, put/call) · `cusip_map`.

**미리 알아야 할 한계** ([SEC 13F FAQ](https://www.sec.gov/rules-regulations/staff-guidance/division-investment-management-frequently-asked-questions/frequently-asked-questions-about-form-13f))

- 분기 종료 후 45일 안에만 내면 된다. 화면의 보유는 최대 4개월 전 모습이다.
- 미국 상장 주식·ETF·일부 옵션만 담긴다. 공매도·해외 상장 주식은 빠진다. 국내 종목은 13F로 볼 수 없다.
- 개인이 아니라 운용사 단위다. 여러 매니저가 있는 회사는 한 사람의 판단으로 볼 수 없다.
- 평가액 단위가 과거(천 달러)와 최근(달러)에 달라졌다고 알려져 있어, 적재 시 단위 보정을 확인해야 한다.

**확장 아이디어**: 국내는 DART 대량보유 상황 보고(5% 룰)로 국민연금 등 대형 기관의 지분 변화를 부분적으로 보여 줄 수 있다. 이미 쓰는 OpenDART 키로 받을 수 있는지 확인이 필요하다.

## 2. 투자자 모델링과 종목 평가

목표는 "이 투자자라면 이 종목을 살까?"에 **예측이 아니라 근거 있는 적합도**로 답하는 것이다. 흐름은 "AAPL 상세 → 모델 선택 → 적합도 점수 + 맞는 점·안 맞는 점 + 비슷한 과거 매수 사례"다.

**모델 후보 (3\~5개, 화면에는 스타일 이름만)**

| 화면 이름 (예시) | 원천 운용사 후보 | 예상 특징 |
| --- | --- | --- |
| 오마하 가치형 | Berkshire Hathaway | 저평가 + 높은 수익성, 장기 보유, 높은 집중도 |
| 매크로 모멘텀형 | Duquesne Family Office | 추세·업종 순환, 높은 회전율 |
| 집중 퀄리티형 | Pershing Square | 소수 종목, 브랜드·현금흐름 중시 |
| 역발상 딥밸류형 | Scion 또는 Baupost | 하락 종목 매수, 저PBR |

후보 기준은 13F 8분기 이상 연속 공시, 종목 수 10\~60개, 한 사람의 판단이 뚜렷한 운용사다. 현재도 공시를 이어가는지는 확정 전에 확인한다.

**수치화할 것 (투자자 프로필)**

1. 종목 성향: 매수 시점 종목의 5요소(저평가·수익성·성장성·안정성·주가 흐름) Z점수를 비중 가중 평균. 1차 매력도 팩터를 그대로 재사용한다.
2. 규모·섹터: 시가총액 구간, 섹터 비중과 시장 대비 과대·과소.
3. 행동 특성: 집중도(상위 10개 비중, HHI), 회전율, 평균 보유 기간, 신규 매수 시 52주 고저 대비 위치(역발상 대 추세).
4. 정성 원칙: 주주서한·인터뷰 등 공개 자료에서 LLM으로 원칙을 뽑아 체크리스트로 저장. 원문은 저장·노출하지 않고 출처 링크만 남긴다.

**평가 방식 (단계적)**

1. 1단계 — 규칙·유사도: 종목의 팩터 벡터와 투자자 프로필의 거리를 0\~100으로. 과거 매수 종목 중 가장 비슷한 사례를 함께 보여 준다.
2. 2단계 — 통계 모델: 분기별 "신규 매수한 종목 vs 살 수 있었지만 안 산 종목"으로 로지스틱 회귀 등을 학습. 매수 비율이 매우 낮아 절대 확률보다 "선호도 백분위"로 보여 주는 편이 정직하다.
3. 3단계 — LLM 설명: 점수·근거 JSON만 입력으로 받아 "이 모델이라면 이렇게 볼 것"을 문장으로 쓴다. 점수 자체는 LLM이 정하지 않는다.

**검증**: 학습에 쓰지 않은 최근 분기에서, 실제 신규 매수 종목이 상위 N개 안에 얼마나 들어오는지(hit rate@N)를 무작위 기준과 비교한다.

**데이터 과제**

- 매수 시점 기준 재무·주가(point-in-time)가 필요하다. 지금은 연간(FY) 재무와 최근 일봉 위주라 과거 구간을 더 받아야 한다.
- 미래 정보가 섞이면(look-ahead) 점수가 실제보다 좋아 보인다. 공시일 이후 값만 쓴다.
- 13F 범위가 미국 주식이라 국내 종목은 "성향만 비교"하는 보조 기능으로 제한한다.

**표현 원칙**: 실명 대신 스타일 이름을 쓰고, "해당 인물의 실제 판단이 아니며 투자 권유가 아님"을 결과 카드마다 표시한다.

## 3. 로그인 (JWT + Redis)

지금 배포는 이미 Cloud Run + Supabase PostgreSQL이라, **DB는 그대로 두고 인증만 자체 구현**하는 것이 가장 싸고 변경이 적다. Supabase는 DB로만 쓰고 Supabase Auth는 쓰지 않으면 사용자에게는 보이지 않는다.

**구조 초안**

- 가입: 이메일 + 비밀번호(argon2/bcrypt 해시). 선택으로 Google 로그인을 직접 연동(Google Identity Services)해 가입 부담을 줄인다.
- 토큰: access token 15분 + refresh token 14일(httpOnly 쿠키, 쓸 때마다 교체).
- Redis 용도: refresh token 저장·폐기(로그아웃, 기기 전체 로그아웃), 로그인 시도 제한, 4번 준실시간 가격과 5번 AI 결과 캐시.
- 연결 지점: `get_current_user_id()` 한 곳만 JWT 검증으로 바꾼다. 라우터·서비스·소유권 검사(404)는 그대로 동작한다.
- 게스트 이전: 가입 순간 현재 게스트 쿠키의 관심종목·포트폴리오를 새 계정으로 옮긴다. 로그인 없이 쓰는 게스트 모드는 유지한다.
- 함께 만들 것: 비밀번호 재설정(이메일 발송 서비스 필요), 회원 탈퇴·데이터 삭제, 개인정보 처리방침, 브라우저 설정(테마·지표)의 사용자별 DB 저장.

**비용 비교 (월 기준)**

| 항목 | 선택지 | 비용 | 비고 |
| --- | --- | --- | --- |
| DB | Supabase Free (현재) | $0 | 500MB, 1주 미사용 시 일시정지 ([가격](https://supabase.com/pricing)) |
| DB | Supabase Pro | $25부터 | 8GB 포함, 일시정지 없음 |
| DB | Cloud SQL (가장 작은 공유 코어) | 약 $10 이상 (추정) | 서울 리전 가격 확인 필요, 이전 작업 발생 |
| Redis | Upstash Free | $0 | 월 50만 명령, 250MB ([가격](https://upstash.com/pricing/redis)) |
| Redis | Upstash 종량제 | 10만 명령당 $0.20 | 15분 갱신·캐시 수준이면 수 달러 |
| Redis | GCP Memorystore Basic 1GB | 약 $35 이상 (추정) | Cloud Run 연결에 VPC 커넥터 비용 추가 |

추천은 Supabase(DB) + Upstash(Redis)다. 사용자가 있는 서비스가 되면 Free의 1주 일시정지가 문제가 되므로 Pro 전환 시점을 토의한다. Cloud SQL·Memorystore 가격은 기억에 의한 추정치이므로 GCP 가격 계산기로 확인해야 한다.

## 4. 관심종목 준실시간 가격 (15\~20분)

전체 종목이 아니라 **누군가의 관심종목에 들어 있는 종목만**, 장이 열려 있을 때 15\~20분마다 갱신해 일봉 종가 옆에 작게 보여 준다.

**동작 초안**

1. 대상 목록: 모든 사용자 관심종목의 중복 제거 티커 (상한 예: 200개).
2. 주기: Cloud Scheduler가 15분마다 Cloud Run Job 실행. 이미 쓰는 `exchange-calendars`로 장 시간이 아니면 바로 종료(국내 09:00\~15:30, 미국은 서머타임 반영).
3. 소스: 국내는 이미 쓰는 KIS 현재가 API(`inquire-price`), 미국은 KIS 해외 현재가 또는 yfinance. 미국 시세의 지연·유료 여부는 확인 필요.
4. 저장: Redis `quote:{market}:{ticker}` (가격, 등락, 기준 시각, TTL 30분). 일봉 테이블에는 쓰지 않는다.
5. 화면: "장중 71,300 (+0.8%) · 14:15 기준" 처럼 기준 시각과 "지연" 표시. 값이 없거나 오래되면 일봉만 보여 준다.

**토의할 점**

- "조회 API는 DB만 읽는다" 원칙을 "DB 또는 Redis만 읽는다"로 넓힐지 결정한다. 외부 호출은 여전히 수집 작업에서만 한다.
- 시세 재배포 조건: 거래소 실시간 시세는 외부 게시에 제약이 있어, 15\~20분 지연은 오히려 안전한 선택이다. KIS·yfinance 이용 약관을 확인한다.
- KIS 호출 한도·토큰 갱신을 기존 일봉 수집과 나눠 쓸지, 한 토큰을 공유할지.
- 포트폴리오 평가액에도 장중 가격을 쓸지 (쓰면 손익이 15분마다 바뀜).

## 5. AI(LLM) 요약·분석 보고서

원칙은 **숫자는 DB가, 문장은 LLM이** 만드는 것이다. 1차에서 매력도 근거·`data_quality`를 JSON으로 만들어 둔 것을 그대로 입력으로 쓴다.

**요청하신 기능**

- 종목 요약 카드: 매력도·재무 추이·최근 공시·시장 점수를 3\~5줄로. 종목·날짜별로 한 번 만들어 캐시한다.
- 분석 보고서: 강점·약점·체크포인트·데이터 한계를 고정 양식으로. 사용자가 누를 때 만들고 PDF로 내보낼 수 있게.

**추가로 추천하는 활용**

| 아이디어 | 입력 | 왜 좋은가 |
| --- | --- | --- |
| 공시 한 줄 요약 + 중요도 태그 | DART·SEC 공시 제목·본문 | 지금 "최근 공시 5건"은 제목만 있어 의미를 알기 어렵다 |
| 13F 분기 변화 해설 | 분기별 신규·추가·매도 목록 | "이번 분기 오마하 가치형은 무엇을 했나"를 문장으로 |
| 투자 원칙 추출 | 주주서한·인터뷰 공개 자료 | 2번 모델의 정성 체크리스트를 만드는 유일한 방법 |
| 자연어 스크리너 | "부채 적고 배당 3% 이상인 미국 기술주" | LLM은 필터 JSON만 만들고, 검색은 기존 SQL이 한다 |
| 매매일지 회고 | 매매 이유 메모 + 결과 | 메모를 근거·감정 태그로 분류하고 반복 패턴을 짚는다 (7번) |
| 지표 풀이 툴팁 | "이 종목 PER 35는 무슨 뜻?" | 초보 사용자 이탈을 줄인다 |

**설계 원칙**

- 입력은 DB에서 만든 JSON만. 응답은 구조화 출력(JSON 스키마)으로 받고, 본문 숫자가 입력에 있는지 서버에서 검사한다.
- 캐시: 입력 해시를 키로 DB에 저장. 같은 날 같은 종목은 다시 호출하지 않는다.
- 비용: 요약·분류는 작고 싼 모델, 보고서는 상위 모델. 야간 일괄 생성은 Batch API, 고정 프롬프트는 프롬프트 캐싱으로 줄인다.
- 사용자별 하루 한도(예: 보고서 5회) — 로그인이 있어야 가능하다. 게스트는 캐시된 요약만.
- 품질: 종목 20개 정도의 평가 세트를 두고, 프롬프트를 바꿀 때마다 숫자 일치·금지 표현("사세요")을 자동 검사한다.
- 모든 AI 출력에 생성 시각·데이터 기준일·"투자 권유 아님"을 붙인다.

모델·단가는 착수 시점 기준으로 다시 확인하고, 월 예산 상한을 먼저 정한다.

## 6. React 전환과 UI 개선

API 계약(`/api/v1`)은 그대로 두고 화면만 바꾼다. 한 번에 갈아엎기보다 페이지 단위로 옮기며, 새 기능(투자자·매매일지)은 처음부터 React로 만든다.

**스택 후보**

- 빌드: Vite + React + TypeScript. 빌드 결과를 지금처럼 FastAPI가 정적 파일로 서빙하면 Cloud Run 구성이 그대로다.
- 데이터: TanStack Query (캐시·로딩·에러 상태 통일, 15분 가격 갱신에 적합).
- 타입: FastAPI OpenAPI에서 TS 타입을 자동 생성해, 백엔드 응답 필드가 바뀌면 프론트 빌드에서 바로 걸리게 한다. 지금 `check_contract.py` 역할을 프론트까지 넓히는 효과.
- 차트: 금융 차트는 TradingView Lightweight Charts, 일반 차트는 Recharts 또는 기존 Chart.js 유지 중 선택.
- 스타일: 기존 CSS 변수 디자인 토큰(라이트·다크)을 옮기고, Tailwind 또는 CSS Modules 중 하나. 컴포넌트는 shadcn/ui 같은 복사형 라이브러리.

**"부드럽고 아름다운"을 구체화하기**

- 스켈레톤 로딩, 숫자 변화 애니메이션, 페이지 전환 시 깜빡임 없음.
- 목표 수치를 정한다: Lighthouse 성능 90+, 첫 화면 2초 이내, 모바일 390px 가로 스크롤 없음(1차 기준 유지).
- 디자인 시안(Figma 등)을 먼저 만들고 구현한다. 시안 없이 구현부터 하면 화면마다 스타일이 달라진다.

**주의**: 팀 규칙의 "빌드 없음·바닐라 JS" 전제가 바뀐다. 입문자 팀원에게 필요한 React·TS 사전 학습 기간과, CLAUDE.md·`team/` 템플릿 갱신을 일정에 넣어야 한다.

## 7. 포트폴리오 강화

지금의 포트폴리오는 "담아 보는 계산기"다. 2차에서는 \*\*거래 원장(매수·매도 기록)\*\*을 중심에 두고, 보유 현황·통계는 원장에서 계산하는 구조로 바꾼다.

**유명 투자자 포트폴리오 가져오기**

- 13F 최신 분기 비중을 내 시드에 맞춰 모의 포트폴리오로 복사한다 (상위 N개만, 최소 비중 이하 제외, 남는 돈은 현금).
- 복사 후 "가져온 그대로 두었다면" 수익률과 원본 투자자의 다음 분기 변화를 비교해 보여 준다.
- 화면에 "이 비중은 최대 4개월 전 기준"을 항상 표시한다.

**매매일지**

- 거래 기록: 날짜, 매수/매도, 수량, 가격, 수수료·세금, 환율(기존 "담는 순간 값 복사" 원칙 유지), 매매 이유 메모, 태그, 확신도.
- 입력 부담 줄이기: 증권사 거래내역 CSV 가져오기 (증권사별 형식 매핑 필요).
- 포트폴리오 종류 구분: 모의 / 실제 / 투자자 따라하기.

**통계**

| 묶음 | 지표 |
| --- | --- |
| 수익 | 실현·미실현 손익, 기간 수익률(TWR), 내 돈 기준 수익률(XIRR), 가격·환율 효과 |
| 위험 | 최대 낙폭(MDD), 변동성, 섹터·통화 편중 |
| 습관 | 승률, 평균 이익/손실 비, 평균 보유 기간, 회전율, 매수 후 20일 수익 |
| 비교 | KOSPI·S&P 500 대비 초과 수익, 투자자 모델과의 스타일 거리 |

**AI 분석**

- 월간 회고 리포트: 위 통계 + 매매 이유 메모를 입력으로 "잘한 점·반복되는 실수·다음달 체크포인트".
- "내 투자 스타일은 어느 모델과 비슷한가": 2번의 프로필 계산을 내 매수 기록에도 적용한다. 1·2·7번을 하나로 엮는 기능이다.

**전제**: 실제 보유 내역은 민감 정보다. 로그인 필수, 탈퇴 시 완전 삭제, 내보내기 기능을 함께 만든다. 기존 모의 포트폴리오 데이터를 새 원장 구조로 옮기는 마이그레이션도 필요하다.

## 2차 착수 전에 필요한 것

요구사항 정의 전에 "무엇을 근거로 우선순위를 정할지"와 "바뀌는 전제"를 먼저 정리해야 한다. 통상 회고 → 현황 측정 → 우선순위 → 설계 결정 순서로 진행한다.

**회고와 기술 부채**

- [ ] KPT(유지·문제·시도) 회고 — 기술뿐 아니라 4인 협업 방식(단계별 분담, 계약 검사)도
- [ ] 기술 부채 목록화: pykrx·yfinance 비공식 의존, KIS 운영 전환, 분기 재무 미구현, 수정주가 소급, 원문 SQL 마이그레이션 관리 방식
- [ ] 1차 미완 선택 기능 3개(분기 재무·투자 스타일 체크리스트·시나리오 API)를 2차에 흡수할지 결정 — 체크리스트는 2번과 거의 같다

**현황 측정 (비교 기준선)**

- [ ] 사용 지표 수집 도입: 방문 수, 페이지별 체류, 기능 사용 빈도 (지금은 측정 수단 없음)
- [ ] 성능·운영 지표: API 응답 시간, 수집 Job 성공률, DB 크기·연결 수, 월 비용
- [ ] 사용자 피드백: 발표 피드백 정리 + 지인 5\~10명 사용성 테스트

**범위·일정**

- [ ] 2차 기간·인원·역할 확정, React·TS 학습 기간 포함
- [ ] 아이디어 7개를 임팩트×노력으로 평가하고 MoSCoW(필수·권장·선택·제외)로 나눔
- [ ] MVP 정의: 데모에서 반드시 보여줄 시나리오 1\~2개 (예: AAPL → 모델 선택 → 평가)

**설계 결정 기록 (ADR)**

- [ ] 인증 방식, Redis 제공자, 프론트 구조(서빙 방식·레포 구조), LLM 공급자·모델, 13F 수집 방식, 거래 원장 모델을 한 장씩 기록

**데이터·법적 검토**

- [ ] 데이터 약관: yfinance(비공식), KIS 시세 재게시, SEC 호출 정책, 제3자 데이터를 LLM에 넣는 것의 허용 여부
- [ ] 자본시장법상 유사투자자문 해당 여부 — "살 확률", AI 보고서 문구가 개별 종목 추천으로 읽히지 않게 표현 기준 마련
- [ ] 실존 인물 이름·사진 사용 기준 (모델명은 스타일 이름)
- [ ] 개인정보보호법: 회원가입 동의, 처리방침, 탈퇴·파기

**인프라·품질**

- [ ] 스테이징 환경 + GitHub Actions 자동 배포
- [ ] 오류 추적·가동 감시(Sentry 등), GCP 예산 알림, LLM 비용 상한
- [ ] 테스트 전략 확장: React E2E(Playwright), 프론트 타입 계약, LLM 평가 세트
- [ ] 인증 보안 점검: 쿠키 CSRF·CORS, 로그인 시도 제한, 비밀 관리

**팀 운영**

- [ ] CLAUDE.md·`team/prompts`·`check_contract.py`를 React·TS·로그인 전제로 갱신
- [ ] 2차 산출물 목록: 요구사항 정의서 v2, ERD 변경분, API 정의서 v2, 화면 설계(와이어프레임), 투자자 모델 정의서(09 매력도 정의서와 같은 형식)
